## Mô hình lỗi

Mọi lỗi rời API ở dạng `application/problem+json` với `{type, title, status, detail, instance, code, request_id, errors[]}`: `type = urn:meshguard:problem:<code>`; `title` cố định theo `code` (tiếng Anh — client dựa vào `code`); `detail` do code của ta viết; `instance` = path của request **không kèm query string** (query có thể chứa credential như OAuth `code`); `request_id` = header `X-Request-Id`. Kèm `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, và `Retry-After` khi có. Status luôn là status §13.1 gán cho `code` (test kiểm bất biến này với spec):

| `code` | Status |
|---|---|
| `unauthenticated`, `reauth_required` | 401 |
| `forbidden`, `tenant_suspended`, `quota_exceeded` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| `precondition_failed` | 412 |
| `validation_failed`, `idempotency_key_reuse` | 422 |
| `precondition_required` | 428 |
| `rate_limited` | 429 |
| `internal_error` | 500 |
| `not_implemented` — **ngoài enum của spec** (Quyết định 1) | 501 |
| `upstream_rejected` | 502 |
| `instance_unavailable` | 503 |

| Tình huống | Problem |
|---|---|
| Tham số path/query/header/cookie sai (bind của code sinh) | `422 validation_failed`, `errors[{field: <tên tham số>, code: invalid_format \| required \| too_many_values}]` |
| Body JSON hỏng, sai kiểu, rỗng, quá giới hạn | `422 validation_failed`, field `body` (hoặc đường dẫn trường an toàn như `given_name`), code `invalid_json` / `invalid_type` / `required` / `too_large` |
| Path hoặc method không có trong spec | `404 not_found` |
| Operation chưa có handler | `501 not_implemented`, `detail` nêu tên operation |
| Handler trả `*problem.Error` (kể cả khi bị wrap) | đúng problem đó |
| Handler trả lỗi khác; panic | `500 internal_error` với `detail` chung; nội dung lỗi chỉ vào log (đã che) |
| Vượt hạn mức | `429 rate_limited` + `Retry-After` + `RateLimit-*` |

## Rate limit

| Lớp | Nhận diện (segment path như ServeMux, sau unescape — `%61uth` vẫn là `auth`) | Mỗi IP | Mỗi identity |
|---|---|---|---|
| `default` | mọi request khác | 50/s, burst 300 | 10/s, burst 100 |
| `auth` | `/api/v1/auth/*` | 2/s, burst 30 | 1/s, burst 20 |
| `enrollment` | `/api/v1/tenants/{t}/enrollment/*` (endpoint có từ Phase 4) | 1/s, burst 10 | 1 mỗi 5 s, burst 5 |
| `sync` | `POST …/devices/sync` và `GET …/devices?fresh=true` | 1 mỗi 2 s, burst 10 | 1 mỗi 10 s, burst 3 |

- Header: `RateLimit-Limit` = burst; `RateLimit-Remaining` = số request còn được phép ngay; `RateLimit-Reset` = số giây tới khi bucket đầy lại; `Retry-After` (chỉ ở 429) = số giây tới token kế tiếp (tối thiểu 1). Header có ở mọi response đã qua một tầng limit và lấy theo bucket gần cạn nhất. Go chuẩn hóa tên thành `Ratelimit-Limit`… (tên header HTTP không phân biệt hoa thường).
- Khóa: IPv4 theo địa chỉ; IPv6 gộp theo /64; identity theo khóa hook session truyền cho `SetIdentity` (`identities.id`, không bao giờ là session id).
- IP client: địa chỉ peer; chỉ khi peer thuộc `TrustedProxies` mới đọc `X-Forwarded-For` và lấy mục ngoài cùng bên phải không phải proxy tin cậy — mục bên trái do client tự đặt bị bỏ qua.
- Bộ nhớ: bucket đã đầy bị quét mỗi phút; tối đa 100 000 khóa mỗi bucket (`Options.RateLimitKeys`); chạm trần thì một khóa bất kỳ bị loại (bucket của nó coi như đầy) — bộ nhớ và CPU bị chặn trên kể cả khi bị flood bằng địa chỉ mới.

- Lỗi dự kiến: trả `problem.New(gen.ProblemCodeNotFound, "…")`, `problem.Validation(detail, problem.Field(…))` hoặc `&problem.Error{…, Cause: err}` (Cause chỉ vào log); lỗi khác ⇒ 500, nội dung chỉ vào log.
- Nơi đặt code: handler set phải nằm dưới `internal/httpapi/…` (ví dụ `internal/httpapi/devicesapi`), vì module nghiệp vụ không được import `httpapi` (§13.6, `internal/archtest`); handler gọi service interface của module nghiệp vụ.
- Spec thêm operation ⇒ `var _ gen.StrictServerInterface = dispatcher{}` không compile cho tới khi operation được thêm vào một interface và vào `NotImplemented`; `TestHandlerGroupsFollowSpec` giữ cách chia khớp `x-task` của spec.

```go
// apps/internal/runner/runner.go — khi các task tương ứng xong
api, err := httpapi.New(httpapi.Options{
	Logger:         log,
	TrustedProxies: cfg.TrustedProxies,
	Handlers: httpapi.Handlers{
		Auth:    authapi.New(identitySvc),   // P2-T06, hiện thực httpapi.AuthHandlers
		Devices: devicesapi.New(devicesSvc), // P2-T13
	},
	Hooks: httpapi.Hooks{
		Session: sessionMiddleware, // P2-T06: principal vào context + httpapi.SetIdentity(ctx, identityID)
		CSRF:    csrfMiddleware,    // P2-T06
		Authz:   authzMiddleware,   // P2-T07: gen.StrictMiddlewareFunc
	},
})

// internal/httpapi/devicesapi — set một phần: operation chưa viết vẫn trả 501
type handlers struct {
	httpapi.NotImplemented
	svc devices.Service
}

func (h handlers) GetDevice(ctx context.Context, req gen.GetDeviceRequestObject) (gen.GetDeviceResponseObject, error) {
	d, err := h.svc.Get(ctx, req.TenantId, req.DeviceId)
	if errors.Is(err, devices.ErrNotFound) {
		return nil, problem.New(gen.ProblemCodeNotFound, "Device not found.")
	}
	if err != nil {
		return nil, err // 500 internal_error; nội dung lỗi chỉ vào log, đã che
	}
	return toGetDevice200(d), nil
}
```

### Hook

| Hook | Kiểu | Hợp đồng |
|---|---|---|
| `Session` | `func(http.Handler) http.Handler` | Chạy sau limit theo IP và giới hạn body. Tự trả 401 bằng `httpapi.WriteProblem(w, r, problem.New(gen.ProblemCodeUnauthenticated, …))` khi cần; khi có phiên hợp lệ gọi `httpapi.SetIdentity(r.Context(), identityID)` — khóa ổn định, không phải secret |
| `CSRF` | `func(http.Handler) http.Handler` | Chạy trước router; từ chối bằng `httpapi.WriteProblem(…, problem.New(gen.ProblemCodeForbidden, …))` |
| `Authz` | `gen.StrictMiddlewareFunc` | Nhận tên operation dạng Go (`ListDevices`) ⇒ tra `x-permission` (ghi chú 10 của P2-T02); tenant lấy từ `r.PathValue("tenantId")` (đã qua bind UUID) hoặc request typed; từ chối bằng `return nil, problem.New(…)` |

**Deny-by-default**: `httpapi.New` trả lỗi khi `Handlers` có set nào được mount mà `Hooks.Authz == nil` — không operation nào chạy được mà bỏ qua kiểm quyền (§8.4 bất biến 4). Test mount handler phải truyền rõ một hook `Authz`.

### Hàm dùng chung

- `requestid.From(ctx)` — request id cho `audit_events.request_id` (P2-T08) và job (P2-T12) ("đi xuyên log, audit, job" — §13.1).
- `httpapi.Operation(ctx)` — tên operation dạng Go; `httpapi.ClientIP(ctx)` — IP client đã xét proxy tin cậy.
- `log.InfoContext(ctx, …)` với logger của `logx` tự thêm `request_id`.

## Quyết định và điểm mơ hồ

1. **501 `not_implemented`**: §13.1 không có mã cho operation chưa có handler và enum `ProblemCode` của spec cũng không có. Theo chỉ đạo của lead: 501 + `not_implemented`, khai ở `problem.CodeNotImplemented`; `TestCatalogFollowsSpec` chỉ cho phép đúng mã này nằm ngoài enum. Cần lead: thêm `not_implemented` (501) vào enum và mô tả của `ProblemCode` (thay đổi cộng thêm, sinh lại Go/TS) — hoặc bảo đảm mọi operation có handler trước khi mở API (P2-T16).
2. **405 ⇒ 404**: §13.1 không có mã cho method không được phép. Mọi request không khớp route sinh (path lạ hoặc method không khai) trả `404 not_found` (RFC 9110 cho phép 404 thay 405), nên status luôn đúng cặp của §13.1 và không còn body plain-text của ServeMux. Bảng route của P2-T02 (`…:expire` ⇒ 405) vẫn đúng với handler sinh đứng riêng; listener public nay trả 404.
3. **400/413 ⇒ 422**: §13.1 không có mã cho 400/413. JSON hỏng, sai kiểu, body rỗng, body quá lớn đều là `422 validation_failed` với `errors[].code` (`invalid_json`, `invalid_type`, `required`, `too_large`). Writer xử lý được mọi status nhưng chuỗi middleware không phát 400/413.
4. **`instance`** = path đã escape, không kèm query; **`title`** tiếng Anh, cố định theo mã.
5. **Header `RateLimit-*`** gửi ở mọi response đã qua tầng limit (spec chỉ khai ở 429 — header thêm không phá contract), theo dạng ba header mà spec dùng: Limit = burst, Reset = tới khi bucket đầy lại.
6. **Lớp chặt hơn**: `auth/*`, `enrollment/*`, `devices/sync`, và `GET …/devices?fresh=true` (§13.1 ghi `fresh=true` có giới hạn tần suất). Giới hạn thêm theo membership cho `enrollment/web-auth/claim` (§13.1) thuộc P4-T06, có thể dùng lại `kit/ratelimit`. Các con số mặc định là điểm khởi đầu, chỉnh ở P6-T07 cùng giới hạn của edge.
7. **Thứ tự rate limit theo IP trước session**: bảo vệ việc tra session (truy vấn DB) khỏi flood; limit theo identity chạy sau hook session.
8. **`MG_TRUSTED_PROXIES` bắt buộc cho `api` ngoài dev**: sau edge mọi request đến từ IP của edge; thiếu cấu hình này thì bucket theo IP thành một bucket chung cho mọi client (một client có thể làm cả API trả 429). P2-T16 phải đặt `MG_TRUSTED_PROXIES=10.249.0.2` (IP tĩnh của edge trên `mg-edge`, [networks.sh](../../../infrastructure/host/networks.sh)) và route `/api/v1` ở edge phải gửi `X-Forwarded-For` (mặc định của `reverse_proxy` trong Caddy).
9. **Lỗi bind xảy ra trước authz**: code sinh (std-http) bind tham số trước strict middleware, nên client chưa xác thực gửi tham số sai nhận 422 thay vì 401 (không lộ dữ liệu; P2-T02 đã ghi nhận). P2-T07 quyết định có cần chặn sớm hơn không.
10. **Không kiểm schema ngoài kiểu**: code sinh chỉ bind theo kiểu Go; `enum` (ví dụ `scope`), `pattern`, `maxLength`, `minimum/maximum` (ví dụ `limit ≤ 200`) **không** được kiểm tự động. Handler phải tự kiểm (`.Valid()` của enum…) hoặc một task sau thêm validator OpenAPI (kin-openapi đã có trong đồ thị module qua oapi-codegen).
11. **`X-Request-Id` của client** được tin khi đúng định dạng (§13.1 "sinh nếu thiếu"), nên nó có mặt trong log và audit — không phải kênh secret; test canary không đặt canary ở header này.
12. **Phạm vi của redaction**: logx che theo tên khóa và theo mẫu nhận diện được (§16.5). Một secret ngẫu nhiên nằm trơ trọi trong chuỗi lỗi (không đi kèm `Bearer`, `token=`, `hskey-`…) thì không thể nhận diện — code tạo lỗi không được đặt secret vào lỗi (§7.6). Lỗi 5xx được log đầy đủ (đã che) vì §13.4 yêu cầu thông điệp gốc chỉ ghi vào log nội bộ.
