## Cách chạy

```bash
make e2e-functional                                                     # runner GitHub / máy dev có docker không cần sudo
DOCKER="sudo docker" E2E_PREFIX=p2t01a E2E_WORK=$HOME/p2t01a-work \
  E2E_OUT=$HOME/p2t01a-out make e2e-functional                          # VM build
python3 tests/e2e/harness/e2e.py up | test | down | render              # từng bước (test chạy lại được trên stack đang chạy)
```

Cần `docker` (Compose ≥ 2.24 cho `!reset`, Engine ≥ 28 cho `gw_priority` của bản render), `python3` ≥ 3.11, `openssl`.
Thoát ≠ 0 nếu một ca FAIL; `all` luôn lưu log đã che secret vào `E2E_OUT` rồi gỡ mọi container/network/volume/thư mục làm
việc của tiền tố (`E2E_KEEP_CACHE=0` gỡ cả hai volume cache Go). Hai lượt cùng tiền tố không chạy chồng nhau (khóa
`<work>.lock`); stack thứ hai song song: tiền tố khác + `MG_E2E_NET_BASE`/`MG_E2E_TENANT_NET` khác.

## Thiết kế stack

**Ghép từ bản render thật.** Harness render bằng chính các tool của repo từ môi trường `ci` rồi ghép file compose theo thứ
tự `render/tenant-a/compose.yaml`, `render/tenant-b/compose.yaml`, `render/edge/compose.edge.yaml`,
`render/idp/compose.idp.yaml`, `compose.yaml` (file sau ghi đè file trước). Service của bản render giữ nguyên image, user,
rootfs chỉ đọc, `cap_drop`, healthcheck; `compose.yaml` chỉ đổi tên container, nguồn bind (`<work>` thay `/opt/meshguard`),
file secret, và bỏ cổng publish của edge (`ports: !reset []`). IP tĩnh của edge/subnet nội bộ là hằng số của
`render_edge.py` (bố cục host thật) — harness thay hằng số đó bằng subnet của stack trước khi render (`render_idp.py` dùng
chung dict nên `KC_PROXY_TRUSTED_ADDRESSES` = IP edge của stack). `test_stack.py` khẳng định Caddyfile của CI chỉ khác bản
render thường ở khối `tls` (diff đúng 5 dòng).

Subnet là tham số (`ci.env`: `MG_E2E_NET_BASE=10.231`, `MG_E2E_TENANT_NET=10.250.231.0/28`), không chồng `10.249/16` của
host thật, stack thử của `tests/idp` và contract test; harness từ chối `10.249`/`10.250` làm base.

**Thứ tự khởi động** (theo §11.3): network do harness tạo (`--internal` cho tenant/data/admin/obs/sec/idp-data) → IdP khởi
động nền + build `dbinit` → PostgreSQL + migration → hai Headscale healthy → **áp `bootstrap-policy.hujson` (deny-all)** →
edge + stund → **edge được gắn vào network tenant lúc chạy** (`docker network connect`, không reload Caddy — §14.6) → chờ
IdP healthy → tạo user + 4 pre-auth key một lần → khởi động client.

**CA nội bộ — chỉ cho CI.** Client chính thức trên thiết bị thật chỉ tin chứng chỉ công khai (X-8, CL-02), nên mọi triển
khai thật dùng ACME (DNS-01, §15.4); stack CI không có domain công khai nên dùng một CA **sinh mới mỗi lượt** bằng `openssl`:
EC P-256, hạn 1 ngày, `pathlen:0`, **name constraint chỉ `DNS:mesh.meshguard-ci.test`** (TLD `.test` dành riêng — RFC 2606),
ký đúng một chứng chỉ `*.mesh.meshguard-ci.test` (serverAuth, hạn 1 ngày) rồi **khóa CA bị xóa ngay** — trong lúc chạy
không ai ký thêm được chứng chỉ nào, và kể cả lộ ra chứng chỉ CA cũng chỉ bao được một domain không tồn tại. Không file nào
của CA được commit; thư mục làm việc bị xóa khi gỡ stack. Client tin CA bằng `SSL_CERT_FILE=/etc/mg-ci-ca/ca.crt` và
`SSL_CERT_DIR=/etc/mg-ci-ca` (thư mục chỉ chứa `ca.crt`, mount chỉ đọc) — kho gốc của Go trong `tailscaled` chỉ còn đúng CA
này; harness kiểm TLS phía host bằng `ssl.create_default_context(cafile=ca.crt)` (cũng chỉ tin CA này).

**Secret.** Sinh mới mỗi lượt bằng `secrets` của Python (40 ký tự `[A-Za-z0-9]`): mật khẩu superuser PostgreSQL (hai bản —
postgres và dbinit), 9 mật khẩu role DB, mật khẩu DB + superuser + admin khởi tạo của Keycloak (`keycloak.conf`), token
admin/metrics của edge, khóa bouncer và token DNS (giả — không dùng), khóa TLS của edge; pre-auth key (4 client + 2 cho
E2E-14) và API key (E2E-12/13) lấy từ CLI Headscale trong container (§25.1 quy tắc 7, ngoại lệ Phase 1–2) qua pipe, không
in ra. Mỗi file 0400, chủ sở hữu là UID của consumer (container alpine trợ giúp `chown`), gắn vào container dạng file
(`secrets:` của compose hoặc bind chỉ đọc); biến môi trường chỉ mang **đường dẫn** (`TS_AUTHKEY=file:/run/secrets/authkey`,
`POSTGRES_PASSWORD_FILE`). Request tới listener admin (E2E-13) được harness ghi sẵn thành file — không secret nào nằm trong
dòng lệnh. Log thu vào artifact bị che theo **giá trị** của mọi secret của lượt chạy + mẫu `hskey-…`/`Bearer`, rồi E2E-16 dò
lại toàn bộ artifact (tệp còn secret bị xóa nội dung và ca FAIL).

**Đổi sang Headscale đã vá (P2-T10a).** Image Headscale là tham số `MG_E2E_HEADSCALE_IMAGE` do harness lấy từ
`versions.lock`: `[images.mg-headscale]` nếu mục này tồn tại, ngược lại `[images.headscale]` (hàm `headscale_lock_key`,
có test). Khi P2-T10a pin `[images.mg-headscale]`, stack tự dùng bản vá mà không sửa file nào khác; ép bản chính thức bằng
`E2E_HEADSCALE_LOCK_KEY=headscale`.

## Giới hạn (vì sao chỉ "functional")

- Cùng một host: client và Headscale chung host (HS-24); "đường trực tiếp" của E2E-11 là bridge Docker, không phải P2P qua NAT; relay ở E2E-10 là ép buộc bằng `TS_DEBUG_ALWAYS_USE_DERP`. Bằng chứng mạng thật vẫn là P1-T12 và các gate G1/G5.
- Client chạy userspace networking (không TUN): bộ lọc gói của client vẫn áp cho netstack (E2E-09/15 chứng minh), nhưng không thay được thiết bị thật.
- IdP: kiểm import 3 realm qua discovery/JWKS; đăng nhập TOTP thật đã có ở P2-T05 (`tests/idp`). Template edge chưa có site `auth.<domain>` nên IdP chưa đi qua edge trong stack.
- Chưa tích hợp vào stack: IT-07/IT-08 (cần P4-T12/P5-T05a), IT-09 (`derpprobe`), IT-14 (§22.1 dự kiến chạy functional hằng đêm trên stack này) — đề xuất làm tiếp trên `tests/e2e/harness`.
- Workflow `e2e-functional` (runner GitHub `ubuntu-24.04`) chưa chạy — nhánh chưa được push; các lượt ở trên chạy trực tiếp bằng harness trên VM build `mg-ci-runner`, không qua GitHub Actions.
