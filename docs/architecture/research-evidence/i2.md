> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## I2 - Connectivity model and test methodology (control plane vs data plane, NAT traversal, DERP relay, WireGuard, failure/continuity)

**Tóm tắt của agent:** The connectivity model is confirmed from primary sources. Headscale (control) only distributes keys, endpoints, the DERP map, DNS and packet filters; it never carries tenant traffic. Every peer pair starts on DERP and upgrades to direct UDP when NAT traversal succeeds (expected for no-NAT and easy-easy pairs; easy-hard and hard-hard pairs stay relayed). DERP relays only disco messages and already-encrypted WireGuard packets. Decisions this supports: 1. Path type is operator-verifiable without custom code: `tailscale status` (direct / relay / peer-relay), `tailscale ping` (`via DERP(code)` vs `via ip:port`), `status --json` (CurAddr, Relay, PeerRelay) and client metrics with a `path` label. Give each tenant its own DERP region_code so the evidence names the tenant relay. Use real TCP traffic for ACL tests, because disco and TSMP pings are answered before the packet filter. 2. Forced-relay tests: set TS_DEBUG_ALWAYS_USE_DERP=true in tailscaled's environment, or isolate client networks, which is what Headscale's own DERP tests do. The knobs are an unstable interface and are compiled out on iOS. 3. Embedded DERP per tenant has three structural costs. Control, relay and STUN fail together when a tenant's Headscale stops. A one-node DERP map is a documented single point of failure and probably prevents hard-NAT detection. Each co-hosted tenant needs its own STUN UDP port or IP, and STUN cannot pass through Caddy. Tailscale also says DERP must not sit behind a load balancer, so DERP through Caddy needs a hands-on test. A shared DERP/STUN tier should be planned earlier than "later". 4. Continuity: with control down, established peers keep working until node keys expire, but nothing can be added, changed or revoked. A restarted client only keeps its peers if the `cache-network-maps` node attribute is set. Clients enforce key expiry locally. Headscale's default is no key expiry, so the expiry policy must be chosen deliberately. 5. Revocation: delete and expire are both pushed to connected peers, which drop the WireGuard peer on receipt. No source guarantees latency (Headscale batches for 800 ms, scans expiry every 5 s, and upstream tests allow 30 to 180 s). Peers partitioned from control keep accepting the revoked node. The SLO must be measured and worded as "for peers connected to control". 6. Accounting: Headscale has no byte counters and no network flow logs; per-peer bytes exist only on clients. The portal must not promise usage data without per-device collection. I did not find the embedded DERP's byte counters exported. 7. Peer relays are supported by Headscale 0.29.x through cap/relay grants (clients 1.86+), but the upstream test covers only `head` clients. Nothing was executed; the three acceptance-test recipes are composed from verified commands and output formats. Still needing tests: `only-tcp-443` and `cache-network-maps` via Headscale nodeAttrs, embedded DERP counters, tunnel survival during a full tenant outage, and revocation latency. Large source files (magicsock.go, endpoint.go, local.go, tailcfg.go) were searched and read in targeted sections, not end to end.

## Nhận định

### I2-01 · `VERIFIED` · *critical* — Control vs data plane

- **Nhận định:** The coordination (control) server only distributes public keys, endpoints and policy; it carries no tenant traffic. User traffic flows peer-to-peer over WireGuard or, as fallback, through DERP relays.
- **Bằng chứng:** 'The so-called control plane is hub and spoke, but that doesn't matter because it carries virtually no traffic. It just exchanges a few tiny encryption keys and sets policies. The data plane is a mesh.' Also: 'Tailscale does not route any traffic through the coordination server.'
- **Nguồn:** https://tailscale.com/blog/how-tailscale-works ; https://tailscale.com/docs/reference/coordination-server-down.md

### I2-02 · `VERIFIED` — Control protocol contents

- **Nhận định:** Clients POST RegisterRequest (NodeKey, OldNodeKey, Auth, Expiry, Hostinfo) to /machine/register and MapRequest (NodeKey, DiscoKey, Endpoints, Hostinfo) to /machine/map; streamed MapResponses carry self Node, Peers/PeersChanged/PeersRemoved, DERPMap, DNSConfig, PacketFilter(s), SSHPolicy and ControlTime.
- **Bằng chứng:** tailcfg/tailcfg.go: RegisterRequest (l.1318), MapRequest (l.1436, 'Endpoints are the client's magicsock UDP ip:port endpoints'), MapResponse (l.2006), Node (l.370: Key, DiscoKey, AllowedIPs, Endpoints, HomeDERP, KeyExpiry).
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/tailcfg/tailcfg.go

### I2-03 · `VERIFIED` — Key types

- **Nhận định:** Each client holds a machine key (device identity towards control), a node key (its WireGuard public key, distributed only to permitted peers) and a disco key (NaCl-box key for path discovery); private keys never leave the node.
- **Bằng chứng:** 'On login, clients generate a node private key. This is a separate curve25519 key from the machine key.' 'The public node key is used to configure WireGuard peers.' disco.go header: 'senderDiscoPub [32]byte // nacl public key'.
- **Nguồn:** https://tailscale.com/blog/tailscale-key-management ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/disco/disco.go ; https://tailscale.com/blog/how-tailscale-works

### I2-04 · `VERIFIED` — Control transport and ports

- **Nhận định:** Control uses a Noise IK-based protocol. For an https server URL with no explicit port the client dials port 80 first and starts a port-443 attempt after 500 ms; an explicit port on an https URL disables the port-80 attempt.
- **Bằng chứng:** control/ts2021/client.go l.134-147: httpPort, httpsPort := '80', '443' ... if u.Scheme == 'https' { httpPort = ''; httpsPort = port }. controlhttp/client.go: httpsFallbackDelay returns 500 * time.Millisecond; knob TS_FORCE_NOISE_443.
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/control/ts2021/client.go ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/control/controlhttp/client.go ; https://tailscale.com/docs/concepts/tailscale-encryption.md

### I2-05 · `VERIFIED` · *critical* — DERP payload and visibility

- **Nhận định:** DERP relays only disco messages and already-encrypted WireGuard packets, addressed by node public key; it cannot decrypt them. The relay sees source and destination node keys and packet sizes, and its code keeps packet and byte counters.
- **Bằng chứng:** 'DERP servers relay two types of packets: DISCO packets and encrypted WireGuard packets.' derp.go: 'FrameSendPacket ... 32B dest pub key + packet bytes'. derpserver.go: packetsRecv/bytesRecv per client (l.2089) and server-wide (l.161-162).
- **Nguồn:** https://tailscale.com/docs/reference/derp-servers.md ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/derp/derp.go ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/derp/derpserver/derpserver.go

### I2-06 · `VERIFIED` · *critical* — Connection establishment sequence

- **Nhận định:** Every peer connection starts relayed via DERP: A connects to B's DERP, they exchange direct-connection details through DERP, both attempt NAT traversal, then upgrade to direct UDP; if that fails a peer relay is tried, otherwise traffic stays on DERP. Paths are re-checked periodically.
- **Bằng chứng:** 'All connections start as relayed through a DERP server, and Tailscale then tries to upgrade them to a direct connection. If that fails, Tailscale tries to connect them using a peer relay. If that fails, the connection remains relayed through the DERP server.'
- **Nguồn:** https://tailscale.com/docs/reference/connection-types.md

### I2-07 · `VERIFIED` — STUN, endpoints and disco

- **Nhận định:** Clients use DERP hosts as STUN servers, from the WireGuard socket, to learn their public ip:port. Candidate endpoints (local, STUN, port-mapped) reach peers via control and via CallMeMaybe, a disco message sent only over DERP; disco Ping/Pong probes every candidate and validates paths.
- **Bằng chứng:** disco.go: 'CallMeMaybe is a message sent only over DERP to request that the recipient try to open up a magicsock path back to the sender.' Docs: 'the DERP relay servers function as the STUN servers'.
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/disco/disco.go ; https://tailscale.com/docs/reference/stun-protocol.md ; https://tailscale.com/blog/how-nat-traversal-works

### I2-08 · `VERIFIED` — Path timers in magicsock

- **Nhận định:** In v1.104.7 magicsock pings the best UDP path every 3 s, trusts it for 6.5 s without a pong, then sends on both UDP and DERP; it stops keeping a path alive after 45 s idle and retries a direct upgrade every minute.
- **Bằng chứng:** magicsock.go l.4078-4113: sessionActiveTimeout = 45s, upgradeUDPDirectInterval = 1m, heartbeatInterval = 3s, trustUDPAddrDuration = 6500ms. endpoint.go addrForSendLocked: 'We had a bestAddr but it expired so send both to it and DERP.'
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/wgengine/magicsock/magicsock.go ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/wgengine/magicsock/endpoint.go

### I2-09 · `VERIFIED` · *critical* — Client egress requirements

- **Nhận định:** Clients need outbound TCP 443 to any host (control and DERP), UDP from source port 41641 to any destination (direct WireGuard), UDP to port 3478 (STUN) and optionally TCP 80 (control fast path, captive-portal detection). Usually no inbound ports are required.
- **Bằng chứng:** 'Let your internal devices start TCP connections to *:443.' 'start UDP from :41641 to *:*' 'start UDP to *:3478' 'start HTTP (TCP) connections to *:80 ... It is not mandatory to permit these connections'.
- **Nguồn:** https://tailscale.com/docs/reference/faq/firewall-ports.md

### I2-10 · `VERIFIED` · *critical* — Headscale server exposure

- **Nhận định:** Headscale v0.29.7 must publicly expose tcp/443 (control API and embedded DERP) and udp/3478 (STUN, when embedded DERP is on); tcp/80 is needed only for built-in ACME HTTP-01, tcp/50443 only for remote gRPC, and tcp/9090 metrics must stay private.
- **Bằng chứng:** docs/setup/requirements.md, 'Ports in use': 'udp/3478 - Expose publicly: yes - STUN, required if the embedded DERP server is enabled'; 'tcp/9090 - Expose publicly: no'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/setup/requirements.md

### I2-11 · `VERIFIED` · *critical* — Vendor DERP hosting constraints

- **Nhận định:** Tailscale states custom DERP servers need ports 80, 443 and UDP 3478 open plus ICMP, and must not be behind NAT devices or load balancers, because DERP uses an HTTP upgrade most load balancers do not support. HTTPS and STUN ports are configurable per DERPNode.
- **Bằng chứng:** 'DERP servers require direct internet connectivity and must not be behind NAT devices (such as firewalls) or load balancers.' 'To use other port numbers for HTTPS and STUN, set DERPNode.DERPPort or DERPNode.STUNPort'.
- **Nguồn:** https://tailscale.com/docs/reference/derp-servers/custom-derp-servers.md

### I2-12 · `VERIFIED` · *critical* — Embedded DERP behind a reverse proxy

- **Nhận định:** Headscale serves the embedded DERP at /derp on the control listener and rejects requests lacking an Upgrade: DERP or WebSocket header; a fronting proxy must pass upgrades, while STUN udp/3478 must be exposed directly. The embedded DERP has no /generate_204 on port 80 and no throughput optimisations.
- **Bằng chứng:** app.go: r.HandleFunc('/derp', h.DERPServer.DERPHandler). derp_server.go: 'If headscale is behind a reverse proxy, make sure it is configured to pass WebSockets through.' reverse-proxy.md: 'STUN ... requires udp/3478 to be served publicly.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/app.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/derp/server/derp_server.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/integration/reverse-proxy.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/derp.md

### I2-13 · `VERIFIED` · *critical* — Embedded DERP map entry per tenant

- **Nhận định:** Each Headscale's embedded DERP map entry takes host and DERP port from server_url and its STUN port from derp.server.stun_listen_addr. Defaults: region_id 999, region_code 'headscale', stun_listen_addr 0.0.0.0:3478, verify_clients true with fail-open disabled.
- **Bằng chứng:** derp_server.go GenerateRegion: 'HostName: host, DERPPort: port' and 'localDERPregion.Nodes[0].STUNPort = portSTUN'; NewDERPServer: 'server.SetVerifyClientURLFailOpen(false)'. config-example.yaml l.91-127.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/derp/server/derp_server.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/config-example.yaml

### I2-14 · `VERIFIED` — Behaviour when UDP is blocked

- **Nhận định:** If UDP is blocked, devices cannot connect directly but still communicate through DERP over HTTPS. netcheck abandons STUN after 3 s and measures DERP latency over HTTPS instead, and `tailscale netcheck` reports UDP false.
- **Bằng chứng:** 'If something on the network blocks direct UDP connections, devices can't establish direct connections, but they can still use relayed connections'. netcheck.go: stunProbeTimeout = 3s, 'before switching to HTTP probing, on the assumption that outbound UDP is blocked'.
- **Nguồn:** https://tailscale.com/docs/reference/connection-types.md ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/net/netcheck/netcheck.go

### I2-15 · `VERIFIED` · *critical* — NAT matrix

- **Nhận định:** Documented expectation: direct for No-NAT with any peer and for Easy-Easy NAT; relayed for Easy-Hard and Hard-Hard NAT. Cloud NAT gateways often behave as hard NAT; two peers behind the same CGNAT need hairpinning or port mapping, otherwise they relay.
- **Bằng chứng:** 'Tailscale uses a relayed connection if ... Both devices have a hard NAT configuration. One device has a hard NAT configuration and the other has an easy NAT configuration.' Blog: 'If both hairpinning and port mapping protocols fail, you're stuck with relaying.'
- **Nguồn:** https://tailscale.com/docs/reference/device-connectivity.md ; https://tailscale.com/docs/reference/connection-types.md ; https://tailscale.com/blog/how-nat-traversal-works

### I2-16 · `REQUIRES_VALIDATION` · *critical* — Hard-NAT detection with one STUN server

- **Nhận định:** netcheck needs two IPv4 STUN results to set MappingVariesByDestIP, and its initial plan sends three probes per region cycling over that region's nodes. With a DERP map holding one embedded node all probes hit one server, so hard NAT is probably undetectable.
- **Bằng chứng:** netcheck.go: 'we need at least two IPv4 results overall to determine whether we're behind a NAT that shows us as different source IPs and/or ports'; makeProbePlanInitial: n := reg.Nodes[try%len(reg.Nodes)]. Test: behind a symmetric NAT with an embedded-only DERP map, run `tailscale netcheck --format=json`.
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/net/netcheck/netcheck.go

### I2-29 · `VERIFIED` · *critical* — Control server outage

- **Nhận định:** With control down, existing devices keep communicating directly or via DERP using locally stored keys and cached filter rules until a node key expires; adding devices, refreshing keys, updating policy and revoking keys are impossible. Tailscale's two pages disagree on whether new connections can form.

### I2-30 · `VERIFIED` — DERP outage and single-DERP maps

- **Nhận định:** If a DERP server fails, clients pick another in the region, then the next closest region, using the last DERP map received. Headscale warns that serving only its embedded DERP (derp.urls: []) makes it a single point of failure.
- **Bằng chứng:** derp-servers.md: 'If the DERP region becomes unreachable, the Tailscale client selects the next closest region.' Headscale derp.md: 'there is now just a single DERP server available for clients. This is a single point of failure'.

### I2-31 · `REQUIRES_VALIDATION` · *critical* — Shared fate of embedded DERP and control

- **Nhận định:** Embedded DERP and STUN run inside the Headscale process, so one tenant's Headscale outage removes control, relay and STUN together. How long established direct tunnels then survive, and whether they recover after a NAT rebind, is undocumented.

### I2-45 · `VERIFIED` — WireGuard protocol

- **Nhận định:** WireGuard carries IP packets over UDP only, using the Noise IK handshake (Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s): Curve25519 static and ephemeral keys, ChaCha20-Poly1305 data encryption, optional pre-shared key, and no response at all to unauthenticated packets.
- **Bằng chứng:** 'WireGuard uses the Noise_IK handshake from Noise ... All packets are sent over UDP.' 'the server does not even respond at all to an unauthorized client; it is silent and invisible.'
- **Nguồn:** https://www.wireguard.com/protocol/

### I2-46 · `VERIFIED` — Cryptokey routing, roaming, silence

- **Nhận định:** Cryptokey routing binds each peer public key to AllowedIPs, acting as routing table on send and access-control list on receive. Peers roam by replying to the latest authenticated source endpoint, and WireGuard is silent when idle unless persistent keepalive is enabled.
- **Bằng chứng:** 'when sending packets, the list of allowed IPs behaves as a sort of routing table, and when receiving packets, the list of allowed IPs behaves as a sort of access control list.' Quickstart: 'it is not a chatty protocol'.
- **Nguồn:** https://www.wireguard.com/ ; https://www.wireguard.com/quickstart/

### I2-47 · `VERIFIED` — WireGuard timers and forward secrecy

- **Nhận định:** WireGuard re-handshakes every few minutes for forward secrecy. In the wireguard-go fork pinned by Tailscale v1.104.7: RekeyAfterTime 120 s, RejectAfterTime 180 s, RekeyTimeout 5 s, RekeyAttemptTime 90 s, KeepaliveTimeout 10 s.
- **Bằng chứng:** Protocol page: 'This handshake occurs every few minutes, in order to provide rotating keys for perfect forward secrecy.' device/constants.go: RekeyAfterTime = time.Second * 120; RejectAfterTime = time.Second * 180. go.mod l.128 pins wireguard-go 9e0ab45c16ca.
- **Nguồn:** https://www.wireguard.com/protocol/ ; https://raw.githubusercontent.com/tailscale/wireguard-go/9e0ab45c16ca/device/constants.go ; https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/go.mod

### I2-48 · `VERIFIED` — WireGuard known limitations

- **Nhận định:** Documented WireGuard limitations: no TCP mode, no DPI obfuscation, not post-quantum secure by default, roaming without re-authentication lets an active MITM redirect ciphertext, and handshakes depend on a trustworthy system clock. Tailscale adds TCP fallback via DERP, outside WireGuard.
- **Bằng chứng:** 'WireGuard explicitly does not support tunneling over TCP'; 'WireGuard is not, by default, post-quantum secure.' how-tailscale-works: 'the open source Tailscale node software includes DERP support, which adds this feature.'
- **Nguồn:** https://www.wireguard.com/known-limitations/ ; https://tailscale.com/blog/how-tailscale-works

## Hệ quả thiết kế (agent đề xuất)

- Plan capacity and availability with Headscale as control-only: tenant traffic touches the host only for the relayed fraction, and the embedded DERP is documented as having no throughput optimisations.
- Give every tenant a unique DERP region_code (and region_id in 900-999) so `tailscale ping`, `tailscale status` and metrics name the tenant relay; keep verify_clients true.
- Each co-hosted tenant needs its own STUN UDP port or IP for stun_listen_addr, published directly by Docker; STUN bypasses Caddy and CrowdSec. Vendor firewall guidance assumes UDP *:3478, so non-standard STUN ports may be blocked on restrictive client networks.
- Caddy must pass HTTP upgrades unbuffered and without short idle timeouts for /ts2021 (POST, Upgrade: tailscale-control-protocol) and /derp (Upgrade: DERP or websocket), and must answer port 80 for control hostnames because clients dial 80 first. Tailscale says DERP must not sit behind load balancers, so this needs a hands-on test.
- Add a second, independent DERP/STUN node to every tenant's DERP map early. It removes the single point of failure, gives netcheck two STUN destinations for hard-NAT detection, and keeps relaying alive during a tenant Headscale restart.
- A shared derper across tenants can only call one --verify-client-url, so the central Go backend would have to implement the admission endpoint and check all tenants; decide fail-open vs fail-closed explicitly (derper defaults to fail-open).
- Automate acceptance tests with `tailscale status --json`, `tailscale ping` output and `tailscale metrics print`, sampled during traffic. Use TCP probes, not tailscale ping, for ACL and revocation tests.
- Forced-relay test environments: Linux or Windows clients with TS_DEBUG_ALWAYS_USE_DERP, or isolated Docker networks as upstream does. Mobile clients need network-level UDP blocking. Never depend on the knobs in production.
- In forced-DERP tests rely on ping, status and metrics rather than `tailscale netcheck`, which probes from the CLI process and does not see tailscaled's knobs.
- State the revocation SLO as applying to peers with a live control connection, and measure it. For stronger guarantees combine node delete, auth-key revocation and a policy change, and set a finite node.expiry as an offline backstop.
- Choose the key-expiry policy explicitly: Headscale defaults to no expiry and tagged nodes never expire. The value bounds both how long a control outage is survivable and how long an unreachable peer keeps trusting a revoked node.
- Control-outage runbook: established tunnels continue, but a restarted client loses its peers unless cache-network-maps is set. Evaluate enabling that attribute tenant-wide through nodeAttrs after testing.
- The portal must not present per-device traffic usage sourced from Headscale. If usage is needed later, build an optional collector (for example `tailscale metrics write` with a node-exporter textfile, or scraping port 5252). Keep logtail.enabled false and do not grant data-plane-audit-logs.
- Monitor relay health through client Health strings ('could not connect to any relay server'), `tailscale debug derp <region code>` and Headscale map-response metrics. If relay byte counters are required, export the embedded DERP's expvars or run a standalone derper.
- Peer relays can be offered later as tenant-operated relays through cap/relay grants, reducing platform relay bandwidth; they need clients v1.86+ (Headscale's minimum is v1.80.0) and an open UDP port on the tenant's relay.

## Câu hỏi mở

- Does Headscale 0.29.7's embedded DERP export relay byte and packet counters anywhere (/metrics, /debug/vars)? Test on a running instance.
- Do the `only-tcp-443` and `cache-network-maps` node attributes pass through Headscale 0.29.7 nodeAttrs and take effect on v1.104.7 clients?
- What is the measured revoke-to-block latency (delete vs expire, direct vs relayed, idle vs active peer), and what is the worst case when a peer is partitioned from control?
- During a full tenant outage (control, DERP and STUN down together), how long do direct tunnels survive, do they recover after a NAT rebind or roaming, and what do relayed pairs experience?
- Can peer pairs with no prior session connect while control is down but DERP is up? Tailscale's two pages disagree.
- Does DERP through Caddy (HTTP upgrade) work reliably, including source-address handling, idle timeouts and CrowdSec interaction? Does the port-80-first control dial add delay behind an HTTP-to-HTTPS redirect?
- With one STUN server per tenant, is hard NAT detected at all, and is a non-3478 STUN port reachable from typical client networks?
- Tailscale documents that the DERP server list persists across client restarts; does that hold for clients on Headscale without the netmap cache?
- Do peer relays behave correctly with stable v1.104.7 clients on Headscale 0.29.7? Upstream tests only `head` clients.
- Decision needed: the value of node.expiry, and whether never-expiring tagged nodes are acceptable for tenant servers.
- Decision needed: which client platforms the acceptance tests must cover, given iOS and Android cannot use the environment knobs.
