## I1 - Official Tailscale clients (v1.104.7) against self-hosted Headscale (v0.29.7): platforms, enrolment, TLS, lifecycle, unsupported features, licensing

**Tóm tắt của agent:** Official Tailscale clients (v1.104.7, capability version 148) are a workable data plane for per-tenant Headscale v0.29.7 instances. Headscale lists Linux, BSD, Windows, macOS, iOS, tvOS and Android as supported, enforces only a version floor (v1.80.0 / capability 113, "last 10 releases") and its changelog recommends clients 1.104.4 or newer. The design hinges on five points read from source and docs. 1. Tenant addressing. The client dials only the control URL's host and port, upgrades at the fixed path /ts2021, and keys local login profiles on the exact ControlURL. Each tenant needs its own hostname; path-based tenancy cannot work. A device can hold several tenant profiles, but only one is active at a time. 2. TLS. The client code accepts http://, and certificate errors on the Noise upgrade are only logged. However, the server key is fetched from /key with strict verification (system roots, optional extra roots, then baked-in Let's Encrypt ISRG roots), and DERP always uses verified HTTPS. Use public Let's Encrypt certificates on 443 per tenant. Private CAs work on Linux through the system bundle, are supported in Android code only since April 2026, and are untested on iOS, Windows and macOS. 3. Enrolment differs per platform. Linux, macOS and Windows use `tailscale login --login-server=<URL>`; Windows has no GUI path (registry or MSI `LoginURL` is the alternative). iOS and Android use an in-app custom-server menu. Managed fleets can use the LoginURL and AuthKey policies, which on iOS require an MDM-managed app. Headscale's default web-auth page only shows an admin CLI command, so the portal must drive enrolment through OIDC, pre-auth keys or the auth/register API. 4. Lifecycle. Headscale's default node expiry is 0 (never). Expired or server-deleted nodes push the client into a logged-out NeedsLogin state. Logout deletes ephemeral nodes and expires user-owned ones. `tailscale up` needs --login-server repeated on later invocations; `tailscale set` is the safe way to change single settings. 5. Feature ceiling. Supported: MagicDNS, split DNS, subnet routers, exit nodes, Taildrop, Taildrive, ACLs, grants, tags, auth keys, OIDC, ephemeral nodes, SSH with check mode, peer relays, embedded DERP. Absent: Funnel, Serve/HTTPS certificates, flow logs, tailnet lock, device posture, device approval, app connectors, SSH recording, webhooks, SCIM, Mullvad. The portal must supply its own approval, audit and event features. Commercial caveats: the daemon/CLI and the Android app are BSD-3-Clause, but the Windows, macOS and iOS GUIs are closed source. Tailscale's Terms license "Client Software" for use with the "Tailscale Solution" and forbid commercial exploitation; no public trademark policy was found. Tailscale calls Headscale community-maintained and not part of its supported product, and Headscale says it does not officially support Docker deployment. Legal review is needed before marketing. Not settled by reading: private-CA behaviour on iOS, Windows and macOS; the deprecated `ControlURL` key in Headscale's Apple profiles; profile switching between two tenants on each GUI; and a 1.104.7 smoke test per OS.

### I1-13 · `VERIFIED` · *critical* — 3 TLS

- **Nhận định:** The v1.104.7 control client accepts only http:// or https:// control URLs, and http:// is a handled scheme: it dials the given port (default 80) and drops the HTTPS fallback for private, loopback or localhost hosts.

## Hệ quả thiết kế (agent đề xuất)

- Give every tenant its own control hostname on port 443 (for example a subdomain). The client upgrades at the fixed root path /ts2021 and keys local profiles on the exact ControlURL, so path-prefix tenancy on a shared hostname cannot work and a tenant URL must never change after enrolment.
- Use publicly trusted certificates per tenant hostname, preferably Let's Encrypt (Caddy's default CA): the client falls back to baked-in ISRG roots when the OS store fails. Do not base the product on a private CA: iOS is unproven, Android needs a build from after April 2026, and DERP and the /key fetch both enforce validation.
- Keep port 80 open on tenant hostnames and answer it quickly (redirect, or proxy the /ts2021 upgrade and /generate_204). The client tries cleartext port 80 first and only then 443. The edge must pass a POST with `Upgrade: tailscale-control-protocol`; a CDN proxy such as Cloudflare in front of tenants is ruled out.
- Never serve tenant control URLs over plain http in production even though clients accept it: the /key fetch over TLS is the only step that authenticates the control server's Noise key, and DERP requires HTTPS anyway.
- Do not expose Headscale's default web-auth page as the customer experience. Choose per tenant between OIDC (one provider per instance), portal-issued pre-auth keys (single use, short TTL, ephemeral or tagged variants), or portal approval through POST /api/v1/auth/register.
- The portal should generate copy-paste enrolment instructions per platform and tenant: `tailscale login --login-server=https://<tenant-host> [--auth-key=...]` for Linux, macOS and Windows (Windows needs a shell, or the LoginURL registry value / MSI TS_LOGINURL); in-app menu steps for iOS and Android; LoginURL plus AuthKey policy templates for managed fleets (iOS only through MDM AppConfig).
- Tell users to change settings with `tailscale set`, and that any later `tailscale up --flag` must repeat `--login-server=<tenant URL>` or use the command the CLI suggests; re-authentication is `tailscale up --login-server=<tenant URL> --force-reauth`.
- Use the LoginURL policy only for devices that must be locked to one tenant; it overrides every profile on the device. Staff who work in several tenants (or also use Tailscale SaaS) need per-profile logins and can have only one tenant active at a time.
- Set `node.expiry` explicitly per tenant (Headscale's default is never) and expose expire, extend and disable-expiry per node in the portal through the node expire API. Deleting or expiring a node makes the client show a logged-out state that needs a fresh login.
- Enforce and display a minimum client version (v1.80.0 today) in the portal, and re-check it at every Headscale upgrade because the floor moves with the 'last 10 releases' policy. Recommend clients 1.104.4 or newer, as the Headscale 0.29.7 changelog does.
- Advertise only features Headscale documents as supported. Funnel, Serve/HTTPS certificates, flow logs, tailnet lock, device posture, device approval, app connectors, SSH session recording, webhooks, SCIM and Mullvad are absent, so approvals, events, audit and user lifecycle must be built in the central backend on top of the Headscale API.
- Route `/admin` on each tenant hostname to the tenant's portal page (or hide the menu item with the Windows AdminConsole policy), because clients link their admin console to `<control URL>/admin`. The tenant hostname is also what Headscale sends as the tailnet domain, so choose readable hostnames.
- Privacy claims need care: clients upload logs to Tailscale Inc. until Headscale's first netmap disables it. Keep `logtail.enabled: false`, never grant the data-plane-audit-logs attribute, and document TS_NO_LOGS_NO_SUPPORT=true / --no-logs-no-support for strict customers.
- For test clients use the official image with TS_AUTHKEY (ephemeral or reusable key), TS_EXTRA_ARGS=--login-server=https://<tenant-host>, and either TS_STATE_DIR on a volume (stable identity, add TS_AUTH_ONCE=true) or no state (new node per start). Userspace mode is the default; kernel mode needs /dev/net/tun and NET_ADMIN.
- Each tenant's embedded DERP advertises the STUN port from its own stun_listen_addr and the DERP host and port from its server_url, so tenants sharing one host need distinct public UDP STUN ports and the edge must also proxy the /derp upgrade; a shared DERP removes that per-tenant port cost.
- Treat upstream support as limited: Headscale states it does not officially support Docker deployment and does not use reverse proxies itself, and Tailscale says Headscale is not part of its supported product. The platform owns the Compose, Caddy and client-compatibility test matrix.
- Before any commercial launch obtain legal advice on Tailscale's Terms (Client Software licensed for use with the Tailscale Solution; no commercial exploitation or resale) and on trademark use. Link customers to official download channels instead of redistributing closed GUI binaries, keep BSD notices if open-source builds are redistributed, and use nominative wording without logos.
