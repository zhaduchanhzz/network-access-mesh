## B3 - fzhzyh/headscale-admin: frontend and deployment (MIT, commit 0a4ca5e92c992bc4dff17d84f8c8c12856f1db69)

**Tóm tắt của agent:** The headscale-admin frontend is a conventional, well-typed React 18 SPA (Vite 6, TypeScript strict, TanStack Query 5, Zustand, React Router 6, Ant Design 5 plus Tailwind 3, Recharts, React Flow) of about 11,400 lines in 36 files. It is single-tenant by construction: one panel talks to one Headscale through its own Node/Fastify backend, and no route, query key, API path or WebSocket channel carries a tenant id. All UI text is hard-coded Simplified Chinese with no i18n framework, there is only a light theme, and sub-path hosting is unsupported. Browser security is sound in outline: an httpOnly SameSite=Lax session cookie, an in-memory CSRF token, nothing in web storage, and the panel's own Headscale API key is only ever returned masked. Weak spots are a pre-auth key passed in a GET query string and the plaintext reveal of newly created keys. The pages are coupled to at least 73 panel-specific endpoints with hand-written types, so reusing them means re-implementing that contract in our Go backend. The genuinely reusable parts are the pure ACL VisualEditor (with known gaps), the draft/validate/acknowledge/drift workflow, the version-history semantics, small UI primitives, the WebSocket hook and the fetch client. The access matrix (N-squared browser requests) and the raw editor (plain textarea) should be redesigned. Deployment: the standalone compose file is a hardened single service (non-root, read-only root, all capabilities dropped, loopback bind) that needs HS_URL and HS_API_KEY. The all-in-one image injects Node into the official headscale v0.29.7 distroless image and runs both processes under a Node supervisor that restarts the whole container when either exits, with relaxed hardening. No Docker socket is mounted, and the panel neither edits Headscale's config nor restarts it; DNS records are exchanged through a shared file. The shipped Headscale config uses SQLite with WAL, database policy mode, an embedded DERP region with no upstream DERP map, and a commented OIDC block aimed at the panel's own provider. Backups use the SQLite online-backup API for the panel database but stop the container to copy Headscale's data directory, are unencrypted, and the restore script does not restore Headscale. Tests use synthetic nodes; no real Tailscale client is ever run and there is no CI. The project is young (36 commits, no stars) and documented only in Chinese, with some inconsistencies. Verdict inputs: Option A (unchanged, one panel per tenant) is cheap to start but adds per tenant a Node process, a SQLite store, a hostname, local accounts without SSO and a second policy writer, in a Chinese-only UI. Option B (fork into a central portal) amounts to rewriting the backend and deeply refactoring the frontend on an unproven upstream. Option C (new portal that borrows components and ideas under MIT with attribution) fits the planned Go/PostgreSQL/React architecture best and is the recommended direction. Two points need hands-on tests before design freeze: per-tenant STUN port behaviour of the embedded DERP, and what the pre-auth key list API actually returns.

## Hệ quả thiết kế (agent đề xuất)

- Choose Option C: build a new tenant-aware portal on the same mainstream stack (React, TypeScript strict, TanStack Query, Zustand, React Router) rather than deploying or forking this panel; put the tenant id in the route, in every query key and in the WebSocket channel from day one.
- Add i18n (English default) and theming at project start; retrofitting them is the largest single cost visible in this codebase (about 1,280 hard-coded Chinese lines, one light theme).
- Borrow under MIT with attribution: VisualEditor (after fixing multi-destination rules and adding SSH/grants/autoApprovers handling), ui.tsx primitives, useRealtime.ts, the fetch client, and the draft/validate/acknowledge/drift UX; keep a third-party notices file with the copyright line and MIT text.
- Implement policy analysis in the Go backend: an ACL evaluator service, one batch endpoint for the access matrix (no N-squared browser calls), and a PostgreSQL policy-version table where rollback creates a new version and failed applies are recorded.
- Keep the browser security model seen here: httpOnly SameSite cookie sessions, a CSRF header on writes, no tokens in web storage, API keys never returned after creation; additionally send pre-auth keys only in POST bodies and scrub them from Caddy access logs.
- Generate API types from an OpenAPI description of the Go backend instead of hand-maintaining a types file.
- Do not use the all-in-one pattern: keep each tenant's Headscale in its own official container so portal or UI restarts never restart a control plane; probe Headscale's HTTP /health; bootstrap and rotate API keys from the backend (short expiry, stored encrypted in PostgreSQL) instead of a 999-day key file.
- If a per-tenant panel is ever offered as an operator tool, treat it as a second policy writer: its drift banner will fire on central changes, and it needs a hostname, secrets, local accounts and backups per tenant.
- The tenant Headscale config template can start from the shipped file (SQLite WAL, policy.mode database, embedded DERP) but must set per-tenant DERP region and STUN port, replace the default public resolvers and time zone, pre-create the extra-records file, and enable the oidc block only once the IdP is reachable.
- DNS extra records need a writer co-located with each Headscale (shared volume or small agent) that validates JSON and writes atomically, because Headscale reads a file and fails to start on invalid JSON.
- Backups: use an online SQLite backup for Headscale too (no control-plane stop), include noise_private.key and the DERP key, encrypt and ship off-host, and rehearse restores per tenant; the reference scripts cover none of this for Headscale.
- Build our own E2E harness with real Tailscale client containers per tenant (DNS, DERP, routes, online state); reuse the synthetic-node trick only for fast control-plane tests.
- Reuse the compose hardening block (read-only root, tmpfs, cap_drop ALL, no-new-privileges, loopback binds, required-variable checks, log rotation) for the portal, backend and tenant containers.
- If images from this repository are ever built, regenerate the lockfile against the official npm registry and pin base images by digest.
