# Research Evidence — G1

> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## G1 - Headscale v0.29.7: OIDC, users/identity and node registration behaviour

**Tóm tắt của agent:** Headscale v0.29.7 gives each tenant instance a workable but deliberately thin OIDC integration. An instance binds to exactly one issuer and one confidential client, derives its redirect URI from server_url (<server_url>/oidc/callback, no override), keys users on issuer plus subject, and refreshes name, email, username and picture at every login. Since 0.29.0 an OIDC login ends on a confirmation page where the user must explicitly accept the device; 0.29.4 and 0.29.7 hardened cookies, state reuse and pending-login capacity. Instance-per-tenant with one IdP client (or realm) per tenant therefore fits naturally, including a customer bringing its own IdP. Four gaps cannot be configured away and must be designed around: 1. Groups. The `groups` claim feeds only the `allowed_groups` login gate. The docs state that OIDC groups cannot be used in policy rules. Group-to-ACL mapping has to be compiled by our backend into policy groups that list users. 2. Lifecycle. Headscale talks to the IdP only at boot and inside the login callback. There is no token refresh, no SCIM, no disable flag. The old 180-day `oidc.expiry` was removed in 0.29.0 and `node.expiry` defaults to 0, so devices never expire by default. An offboarded user's nodes are therefore expected to keep working until the backend expires or deletes them through the API. This consequence is inferred from the code, not tested. 3. Device approval. None exists after OIDC login: the machine is always reported as authorised, and upstream request #2176 is open with milestone v0.30. Options are self-confirmation plus a default-deny quarantine policy, or a portal-brokered flow using POST /api/v1/auth/register. 4. MFA. Entirely the IdP's job; Headscale reads no acr or amr claims. Operational constraints that shape the architecture: - Discovery runs at startup with a 30-second timeout. By default the instance refuses to start if the issuer is unreachable; with the flag off it silently runs without OIDC until restarted. - Every OIDC change, including the allowed_* lists, needs a restart; SIGHUP reloads only the policy. A restart drops in-flight logins. - Login filters are empty by default (anyone the IdP authenticates for the client is admitted), exact and case-sensitive, and the group claim name is fixed to `groups`. No custom tenant claim can be checked. - An OIDC login never merges with a CLI- or API-created user of the same name, and duplicate names make name-based policy tokens ambiguous, which 0.29 rejects. Recommendation: use one issuer per tenant, or at minimum one client per tenant plus `allowed_groups`; set `node.expiry` explicitly; generate policy that references users by provider identifier; and treat Headscale as enforcing only issuer, audience and three static login filters. Group mapping, offboarding, approval and MFA policy belong in the central backend and the IdP. Nothing was executed. Three points need hands-on tests before the design is fixed: offboarding behaviour of existing nodes, behaviour when the issuer is down at boot, and whether API registration and user rename behave as the code suggests on an OIDC-enabled instance.

## Nhận định

### G1-01 · `VERIFIED` — config: activation and credentials

- **Nhận định:** OIDC is switched on solely by a non-empty `oidc.issuer` (there is no `oidc.enabled` key). The issuer must be an http(s) URL, and `oidc.client_id` plus either `oidc.client_secret` or `oidc.client_secret_path` (mutually exclusive) are mandatory; violations abort startup.
- **Bằng chứng:** config.go L608-616: 'OIDC is activated by setting oidc.issuer (see app.go), not by a dedicated oidc.enabled key'; validateOIDCConfig L367-388; L1228-1241 reads the secret file with os.ExpandEnv and trims whitespace.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/config.go

### G1-02 · `VERIFIED` — config: scope and extra_params

- **Nhận định:** `oidc.scope` defaults to openid, profile, email. `oidc.extra_params` is a free key/value map appended to the authorization request; the docs use it for `domain_hint` and `prompt: select_account`.
- **Bằng chứng:** config.go L482 sets the default scope to oidc.ScopeOpenID, profile, email; oidc.go L231-234 loops over cfg.ExtraParams with oauth2.SetAuthURLParam; docs/ref/oidc.md section 'Microsoft Entra ID'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/config.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go

### G1-03 · `VERIFIED` · *critical* — config: login filters default

- **Nhận định:** `oidc.allowed_domains`, `oidc.allowed_users` and `oidc.allowed_groups` are empty by default, which means every user the identity provider authenticates for this client is admitted and gets a Headscale user.
- **Bằng chứng:** docs/ref/oidc.md, 'Authorize users with filters': 'Filters are disabled by default, users are allowed to join once the authentication with the identity provider succeeds.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/oidc.md

### G1-04 · `VERIFIED` — config: email verification

- **Nhận định:** `oidc.email_verified_required` defaults to true (added in 0.28.0): an unverified email is not stored, and login is refused with 'unverified email' when a domain or user filter is configured. Setting it to false stores and trusts unverified emails.
- **Bằng chứng:** config.go L487 default true; oidc.go L631-636; CHANGELOG 0.28.0 (#2860): 'When `true` (default), only verified emails can authenticate via OIDC in conjunction with `oidc.allowed_domains` or `oidc.allowed_users`.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/CHANGELOG.md

### G1-05 · `VERIFIED` — config: PKCE

- **Nhận định:** PKCE is disabled by default (`oidc.pkce.enabled: false`) although the docs recommend it; `oidc.pkce.method` defaults to S256 and accepts only `plain` or `S256`. Enabling PKCE also adds the oauth2 offline access-type option to the authorization request.
- **Bằng chứng:** config.go L485-486 defaults, L354-360 validatePKCEMethod ('pkce.method must be either plain or S256'); oidc.go L216-229: `extras = append(extras, oauth2.AccessTypeOffline)` inside the PKCE branch; docs heading 'Enable PKCE (recommended)'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go

### G1-06 · `VERIFIED` — config: use_expiry_from_token

- **Nhận định:** `oidc.use_expiry_from_token` defaults to false. When true, the node key expiry is the ID token's expiry (the docs call it the Access Token) and `node.expiry` is ignored for OIDC-registered nodes, so devices re-authenticate as often as tokens expire.
- **Bằng chứng:** oidc.go L330: `nodeExpiry := a.determineNodeExpiry(idToken.Expiry)`, L490-496; config-example.yaml L401-406: 'enabling this will cause `node.expiry` to be ignored for OIDC-authenticated nodes.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/config-example.yaml

### G1-07 · `VERIFIED` · *critical* — node expiry default

- **Nhận định:** `oidc.expiry` (default 180d through 0.28) was removed in 0.29.0 and now aborts startup if set. Its replacement `node.expiry` covers all non-tagged nodes and defaults to 0, so OIDC-registered devices never expire unless the operator sets a value.
- **Bằng chứng:** config.go L493 sets the node.expiry default to 0; L606 `depr.fatalIfSet` for oidc.expiry; config-example L167 'Default: 0 (no default expiry)'; v0.28.0 config.go L384 default 180d. Config-example L159 still mentions oidc.expiry (stale comment).

### G1-08 · `VERIFIED` — config: environment variables

- **Nhận định:** Every configuration key can be supplied as an environment variable with the `HEADSCALE_` prefix and dots replaced by underscores (for example `HEADSCALE_OIDC_ISSUER`, `HEADSCALE_OIDC_CLIENT_SECRET_PATH`), which suits per-tenant container configuration.

### G1-09 · `VERIFIED` · *critical* — single provider

- **Nhận định:** One Headscale instance supports exactly one OIDC issuer and one client; there is no multi-provider configuration.
- **Bằng chứng:** docs/ref/oidc.md, 'Switching OIDC providers': 'Headscale only supports a single OIDC provider in its configuration, but it does store the provider identifier of each user.' OIDCConfig (config.go L222-235) has a single Issuer and ClientID.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/oidc.md

### G1-10 · `VERIFIED` — claims consumed

- **Nhận định:** Claims read: sub, iss, name, email, email_verified, picture, preferred_username and groups, first from the ID token and then from the UserInfo endpoint. UserInfo values take precedence when its sub matches the ID token; a failed UserInfo call is tolerated.
- **Bằng chứng:** types/users.go L302-314 (OIDCClaims JSON tags), L420-430 (OIDCUserInfo); oidc.go L342-365: merge guarded by `userinfo2.Sub == claims.Sub`, otherwise log 'could not get userinfo; only using claims from id token'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/users.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go

### G1-11 · `VERIFIED` · *critical* — user keying

- **Nhận định:** A Headscale user is keyed by the provider identifier, built as issuer + '/' + subject and looked up in `users.provider_identifier`; email and username play no part in matching. This has been the rule since the 0.24.0 security fix.
- **Bằng chứng:** types/users.go L325-355 (`result = issuer + '/' + subject`); db/users.go L145-148 (query on provider_identifier); CHANGELOG L996: 'Headscale v0.24.0 now identifies OIDC users by the `iss` and `sub` claims.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/users.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/users.go

### G1-12 · `VERIFIED` — profile update on login

- **Nhận định:** Each successful login rewrites the user from claims: display name, picture and provider identifier always; username only if `preferred_username` is valid; email only if verified (or verification is disabled) and parseable. An email stored earlier is not cleared when it later arrives unverified.
- **Bằng chứng:** types/users.go L434-460 FromClaim: 'FromClaim overrides a [User] from OIDC claims. All fields will be updated, except for the ID.'; email assignment only inside the verified branch; oidc.go L708-748 createOrUpdateUserFromClaim.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/users.go

### G1-13 · `VERIFIED` — username rules

- **Nhận định:** A username must be at least two characters, start with a letter and contain only letters, digits, hyphens, dots, underscores and at most one '@'. A missing or invalid `preferred_username` is skipped (blank for new users) and login still succeeds.
- **Bằng chứng:** util/dns.go L36-72 ValidateUsername; types/users.go L435-440 logs 'username %s is not valid' and continues; docs/ref/oidc.md Google warning: 'The username in Headscale will be blank/not set.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/util/dns.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/oidc.md

### G1-14 · `VERIFIED` — conflict with CLI-created users

- **Nhận định:** An OIDC login never adopts an existing CLI- or API-created user with the same name or email; it creates a second user row. The unique indexes allow equal names as long as provider identifiers differ.
- **Bằng chứng:** db/schema.sql L23-39 ('The same username can exist across different providers with different identifiers'); integration/auth_oidc_test.go L250-281 expects local user1 (Id 1) next to OIDC user1 (Id 2, Provider oidc).
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/schema.sql ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/integration/auth_oidc_test.go

### G1-15 · `VERIFIED` — policy references and duplicate names

- **Nhận định:** Policy user tokens resolve by provider identifier first, otherwise by email or username; a token that matches several users is an error and, since 0.29.0, the whole policy is rejected. Duplicate names across local and OIDC users therefore break name-based rules.
- **Bằng chứng:** policy/v2/types.go L404-439 resolveUser returns ErrMultipleUsersFound; CHANGELOG 0.29.0 (#3160): 'Reject policies whose `user@` tokens match multiple DB users'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/policy/v2/types.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/CHANGELOG.md

### G1-16 · `VERIFIED` — no pre-provisioning of OIDC users

- **Nhận định:** The CreateUser API accepts only name, display name, email and picture URL; it cannot set a provider identifier. OIDC users therefore exist in Headscale only after their first login and cannot be pre-provisioned through the API.
- **Bằng chứng:** headscale.swagger.json v1CreateUserRequest (L1140-1155): name, displayName, email, pictureUrl; grpcv1.go L47-66 builds types.User without ProviderIdentifier.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/gen/openapiv2/headscale/v1/headscale.swagger.json ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/grpcv1.go

### G1-17 · `REQUIRES_VALIDATION` — renaming OIDC users

- **Nhận định:** The database helper refuses to rename OIDC users ('cannot edit OIDC user'), but the gRPC RenameUser handler calls State.RenameUser, which updates the name without that guard. Whether API renames of OIDC users are actually blocked in 0.29.7 needs a test.
- **Bằng chứng:** db/users.go L93-111 ErrCannotChangeOIDCUser; state/state.go L601-607 RenameUser calls UpdateUser directly; grpcv1.go L69-92. Test: POST /api/v1/user/{oldId}/rename/{newName} on an OIDC user, then check the result and the next login.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/users.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/state/state.go

### G1-18 · `VERIFIED` · *critical* — switching issuer

- **Nhận định:** Any change of issuer changes every user's provider identifier; the documented remedy is a manual update of `users.provider_identifier` for each user in the database.
- **Bằng chứng:** docs/ref/oidc.md, 'Switching OIDC providers': 'you will need to manually update the `provider_identifier` column in the `users` table for each user with the appropriate value for the new provider.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/oidc.md

### G1-19 · `UNSUPPORTED` · *critical* — groups in policy

- **Nhận định:** Identity-provider groups cannot be used in the ACL policy. The `groups` claim is consumed only by the `allowed_groups` login gate and is not stored on the Headscale user.
- **Bằng chứng:** docs/ref/oidc.md 'Limitations': 'OIDC groups cannot be used in policy rules.'; claims table: '`groups` | Only used to filter for allowed groups'; docs/about/features.md: '[ ] OIDC groups cannot be used in ACLs'; User struct (types/users.go L66-98) has no groups field.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/oidc.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/about/features.md

### G1-20 · `UNSUPPORTED` · *critical* — group claim format and custom claims

- **Nhận định:** The group claim name is fixed to `groups` and must be an array of strings or a single string. There is no option to rename the claim or to gate login on any other custom claim, such as a tenant identifier.
- **Bằng chứng:** types/users.go L309: Groups field with JSON tag `groups,omitempty`; L245-270 FlexibleStringSlice accepts a string array or one string; OIDCConfig (config.go L222-235) offers only AllowedDomains, AllowedUsers, AllowedGroups.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/users.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/config.go

### G1-21 · `VERIFIED` — gate evaluation order

- **Nhận định:** Login gates run in this order: allowed_groups, then the verified-email precondition (only when a domain or user filter is set), then allowed_domains, then allowed_users. Every configured filter must pass; within allowed_groups one matching group is enough.
- **Bằng chứng:** oidc.go L620-653 doOIDCAuthorization; docs/ref/oidc.md: 'In case multiple filters are configured, a user needs to pass all of them.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/oidc.go

### G1-22 · `VERIFIED` — gate matching semantics

- **Nhận định:** Filter matching is exact and case-sensitive: the domain is the text after the last '@' of the email claim, `allowed_users` compares the email address (not the username), and groups are compared as whole strings.
- **Bằng chứng:** oidc.go L562-603 (slices.Contains on allowedDomains, claims.Groups, allowedUsers); comment L616-617: '[validateOIDCAllowedUsers] only checks the email address -- not the username.'

### G1-23 · `VERIFIED` — what an unauthorised user sees; page branding

- **Nhận định:** A user failing a gate gets HTTP 401 and a fixed Headscale-branded page ('Unauthorized', 'You are not authorized. Please contact your administrator.'). The reason is only logged and no user is created. All browser pages are compiled templates with no branding or language option.
- **Bằng chứng:** handlers.go L41-87 (httpUserError, userMessageForStatusCode); oidc.go L367-383: doOIDCAuthorization runs before createOrUpdateUserFromClaim; templates/auth_error.go, register_confirm.go, auth_success.go are elem-go builders with hard-coded strings.

### G1-24 · `VERIFIED` — expiry enforcement

- **Nhận định:** Key expiry is enforced by a scheduled task running every 5 seconds that marks expired nodes offline; the expired client stays connected to the control server in a needs-login state. A client cannot extend its own key.

### G1-25 · `VERIFIED` — re-authentication flow

- **Nhận định:** Re-authentication repeats the full interactive flow (new auth URL, IdP login, confirmation page) and ends with 'Node reauthenticated'. The same user on the same machine key keeps the existing node; a different user on that machine gets a new node.
- **Bằng chứng:** oidc.go L1100-1122 renderRegistrationSuccessTemplate; state/state.go L2463-2510 ('Creating new node for different user (same machine key exists for another user)'); integration/auth_oidc_test.go L455-460.

### G1-26 · `VERIFIED` · *critical* — no IdP synchronisation after login

- **Nhận định:** Headscale contacts the identity provider only at startup (discovery) and inside the login callback (code exchange, ID-token verification, one UserInfo call). Tokens are neither stored nor refreshed, and nothing re-validates users or group membership in the background.
- **Bằng chứng:** hscontrol/oidc.go read in full (1183 lines): IdP calls only in NewAuthProviderOIDC (L91), getOauth2Token (L521-539), extractIDToken (L541-558) and UserInfo (L342); a search for refresh or TokenSource matches only L220 and L342.

### G1-27 · `REQUIRES_VALIDATION` · *critical* — offboarding effect on existing nodes

- **Nhận định:** Nodes of a user who is disabled or deleted at the identity provider are expected to keep working until their key expires and re-authentication fails; with the default `node.expiry: 0` that means indefinitely.
- **Bằng chứng:** Inference from G1-26 and G1-07; no source states it. Test: register a node via OIDC, disable the user at the IdP, confirm peers stay reachable, then expire the node through the API and confirm re-login is refused.

### G1-28 · `VERIFIED` · *critical* — operator actions for offboarding

- **Nhận định:** Available operator actions: expire a node (`POST /api/v1/node/{nodeId}/expire`, optional `expiry` timestamp), delete a node (`DELETE /api/v1/node/{nodeId}`) and delete a user (`DELETE /api/v1/user/{id}`). User deletion fails while the user still owns nodes.

### G1-29 · `VERIFIED` — no ban, disable flag or provisioning API

- **Nhận định:** Deleting a Headscale user is not a ban: the next successful login with the same issuer and subject creates a new user. The user model has no disabled or suspended state, and the REST API offers only list, create, delete and rename for users.

## Hệ quả thiết kế (agent đề xuất)

- Provision one IdP client per tenant instance with redirect URI https://<tenant-host>/oidc/callback, deliver its secret as a mounted file (oidc.client_secret_path), and treat client creation, config rendering and instance restart as one provisioning transaction.
- Prefer an issuer per tenant (for example a realm per tenant): Headscale then rejects other tenants' tokens by issuer and signing key, a tenant can federate its own corporate IdP, and no login filter is needed. A shared issuer is viable only with a per-tenant client plus allowed_groups or IdP-side client access rules, because Headscale cannot check a tenant claim.
- Decide the issuer model before onboarding users. The provider identifier embeds the issuer URL, so changing it later means rewriting users.provider_identifier in every tenant SQLite database.
- Set node.expiry explicitly in every tenant config. The 0.29 default is no expiry, and key expiry is the only built-in mechanism that sends a device back through the IdP.
- Build offboarding into the central backend: on IdP user disable, delete or group removal, list the user's nodes in the tenant instance, expire or delete them, delete the user and expire the user's pre-auth keys. Add a periodic reconciliation, since Headscale receives no IdP events.
- Implement group-based access in the backend: keep IdP group membership in PostgreSQL, compile it into policy groups whose members are provider identifiers (issuer/subject with a trailing @), and push the policy through the API on every membership change. Users become visible in Headscale only after first login.
- Device approval needs a product decision: (a) accept user self-confirmation and quarantine new devices with a default-deny policy until the portal approves them; (b) leave Headscale OIDC off and let the portal authenticate users and call POST /api/v1/auth/register; or (c) wait for upstream manual approval (#2176, milestone v0.30).
- Enforce MFA in the IdP per realm or client. Optionally send prompt or acr_values through oidc.extra_params, knowing Headscale will not verify the outcome. SSH check mode can add step-up for SSH.
- Choose only_start_if_oidc_is_available deliberately. With true, an IdP outage during a host or container restart keeps the affected tenant control planes down. With false, an instance starts without OIDC and stays that way, so the backend must detect it (for example /oidc/callback returning 404) and restart the instance. If the IdP shares the Compose host, add health-gated start ordering.
- Changing allowed_groups, allowed_users, scopes or the client secret needs a restart that drops in-flight logins. Batch such changes and do not use allowed_users as a frequently edited per-user allowlist.
- At the edge, route per tenant hostname and pass /register/*, /register/confirm/*, /oidc/callback and /auth/* to the right instance; keep server_url on https so cookies are Secure; rate-limit unauthenticated registration attempts to protect the 1024-entry pending cache; set trusted_proxies.
- Do not create local users whose names equal OIDC usernames, and never key generated policy on usernames or emails that users can edit at the IdP; duplicates make 0.29 reject the policy.
- Use tagged pre-auth keys created through the API for servers and automation. They bypass OIDC, their nodes never expire and they survive the creating user's offboarding, so the backend must track and revoke them itself.
- Headscale's browser pages cannot be branded or localised per tenant; put tenant branding on the IdP login page and in the portal.
- Pin tenants to 0.29.7 or later and re-read the changelog on every upgrade: OIDC behaviour changed materially in 0.24, 0.28 and 0.29, and minor versions cannot be skipped.

## Câu hỏi mở

- Decision: issuer per tenant or one shared issuer? This needs the IdP research area's input on realm count limits and automation APIs.
- Decision: which node.expiry value (for example 30d, 90d or 180d) balances re-authentication friction against offboarding latency?
- Test: after a user is disabled at the IdP, do existing nodes keep working until expiry, and does expiring a node through the API cut peer connectivity promptly on all client platforms?
- Test: behaviour of an instance started while the issuer is unreachable under both settings of only_start_if_oidc_is_available, including the interaction with the container restart policy.
- Test: POST /api/v1/auth/register against an OIDC-enabled instance, including OIDC users with blank or duplicate names. Is a portal-brokered approval flow workable, and can the edge redirect /register/{auth_id} to the portal?
- Test: are API renames of OIDC users blocked (the database guard is bypassed on the State path), and does the API validate usernames on create?
- Test: Keycloak groups mapper on the UserInfo endpoint with Full group path on and off, and the exact strings required in allowed_groups.
- Test: do extra_params such as prompt=login, max_age or acr_values force a fresh login or step-up at the chosen IdP when a node re-authenticates?
- Test: the docs say that after switching providers Headscale cannot create users because name and email are already in use, yet the schema has no unique index on email and allows equal names with different provider identifiers. Which is true in 0.29.7?
- Does a path-prefixed server_url work end to end with official clients, or must every tenant have its own hostname? The code builds prefix-aware URLs and cookie paths, but client behaviour was not examined here.
- How should the backend learn a new user's providerId: poll /api/v1/user after login, or compute issuer/subject from the IdP admin API before first login?
- Should interactive OIDC login be offered for unattended devices at all, or only pre-auth keys issued by the portal?
