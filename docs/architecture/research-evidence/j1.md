# Research Evidence — J1

> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## J1 - Shared edge for many Headscale instances on one host: Caddy, CrowdSec, TLS/ACME, DNS, Docker networking

**Tóm tắt của agent:** Decision view. A single shared edge (one custom-built Caddy v2.11.9 plus one CrowdSec v1.8.2, both confirmed as latest releases today) in front of many Headscale v0.29.7 instances is technically sound, with four design-shaping constraints. 1. Upgrades work, reloads hurt. Caddy's reverse_proxy tunnels any HTTP/1.1 Upgrade (the ts2021 POST upgrade and DERP) with no special configuration, but every config reload - caddy reload, POST /load, or any admin-API mutation - closes all upgraded streams of all tenants unless stream_close_delay postpones it; the reload-surviving stream_detached option exists only on Caddy master. Tenant onboarding should therefore not require a reload: use one wildcard site whose upstream is derived from the host label (placeholder or 'dynamic a' upstream). That label is attacker-controlled input and must be regex-checked and prefixed. 2. Certificates. Use one wildcard certificate via DNS-01 (custom xcaddy build with a caddy-dns module; the data volume must persist). Per-tenant certificates under one registered domain run into Let's Encrypt's 50-per-week limit; keep on-demand TLS with an ask endpoint for customer-owned domains. An internal CA is not viable because Tailscale clients verify /key and DERP against system and Let's Encrypt roots; LAN development should use a real domain with DNS-01 and watch resolver rebinding protection. 3. Headscale specifics. Clients try port 80 first and effectively need HTTPS on 443 per hostname; the edge must overwrite True-Client-IP/X-Real-IP and each instance must list the edge in trusted_proxies; an edge path allow-list can hide /api, /swagger and /version, while metrics and gRPC are separate listeners. Embedded DERP advertises the STUN port it listens on, so each tenant needs its own UDP port mapped 1:1, and STUN correctness behind Docker NAT (especially IPv6 through the userland proxy) needs a hands-on test. 4. CrowdSec and Docker. The Caddy bouncer is a third-party module; detection relies on Caddy's JSON access log, which for long-lived streams is written only at close. CrowdSec cannot see inside the Noise tunnel or STUN, bans by source IP for 4 hours across all tenants (NAT risk; allowlists exist), and shares signals with the vendor's Central API unless disabled. Docker's default pools give only 31 subnets, so per-tenant networks need custom default-address-pools; bridges isolate tenants by default; Caddy can be attached to new networks at runtime (pin its default gateway); host firewalling must use DOCKER-USER, not ufw. Rate limiting needs a non-official, unreleased plugin or nftables. Recommendation: shared edge with reload-free wildcard routing first. Run four proofs of concept before committing: label-derived upstream with runtime network attach, reload behaviour with real clients, STUN/netcheck through Docker NAT, and a CrowdSec false-positive replay for NATed client populations.

## Nhận định

### J1-01 · `VERIFIED` · *critical* — Caddy: HTTP Upgrade for non-WebSocket protocols

- **Nhận định:** Caddy v2.11.9 reverse_proxy tunnels any HTTP/1.1 Upgrade protocol, not only WebSocket: it re-adds the client's Upgrade token upstream and switches to a raw bidirectional tunnel when the backend answers 101 with the same token. No extra directive is needed.
- **Bằng chứng:** reverseproxy.go L884-909: `reqUpgradeType := upgradeType(req.Header)` ... `req.Header["Upgrade"] = []string{reqUpgradeType}`; L1311 comment 'deal with 101 Switching Protocols responses: (WebSocket, h2c, etc)'; streaming.go handleUpgradeResponse `asciiEqualFold(reqUpType, resUpType)`. Docs only say: 'The proxy also supports WebSocket connections'.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/caddy/v2.11.9/modules/caddyhttp/reverseproxy/reverseproxy.go ; .../reverseproxy/streaming.go

### J1-02 · `VERIFIED` — Tailscale client upgrade requests

- **Nhận định:** Tailscale v1.104.7 opens control with `POST /ts2021` plus `Upgrade: tailscale-control-protocol` (HTTP/2 explicitly disabled) and DERP with `GET /derp` plus `Upgrade: DERP`; DERP skips the 101 exchange only when TLS 1.3 exposes derper's meta-certificate, otherwise it requires HTTP 101.
- **Bằng chứng:** controlhttp/client.go: '// Disable HTTP2, since h2 can't do protocol switching.' `tr.TLSClientConfig.NextProtos = []string{}`; `Method: "POST"`. derphttp_client.go L497-538: `if cs.Version >= tls.VersionTLS13 { serverPub, ... = parseMetaCert(...) }`, `req.Header.Set("Upgrade", "DERP")`.
- **Nguồn:** https://raw.githubusercontent.com/tailscale/tailscale/v1.104.7/control/controlhttp/client.go ; .../derp/derphttp/derphttp_client.go ; .../control/controlhttp/controlhttpcommon/controlhttpcommon.go

### J1-03 · `VERIFIED` · *critical* — Caddy: streams on config reload

- **Nhận định:** By default every Caddy config reload immediately closes all upgraded streams handled by the old config; only WebSocket streams receive a Close frame, other protocols such as ts2021 and DERP are simply closed.
- **Bằng chứng:** Docs: 'By default, WebSocket connections are forcibly closed (with a Close control message sent to both the client and upstream) when the config is reloaded.' streaming.go: `if h.StreamCloseDelay == 0 { return h.closeConnections() }`; gracefulClose is set only `if isWebsocket(req)`.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/website/master/src/docs/markdown/caddyfile/directives/reverse_proxy.md ; https://raw.githubusercontent.com/caddyserver/caddy/v2.11.9/modules/caddyhttp/reverseproxy/streaming.go

### J1-04 · `VERIFIED` · *critical* — Caddy: stream_close_delay, stream_timeout, stream_detached

- **Nhận định:** `stream_close_delay` postpones closing old-config streams until the delay elapses, then closes all that remain at once; `stream_timeout` caps stream lifetime; both default off. A `stream_detached` option that keeps streams across reloads exists only on Caddy master, not in v2.11.9.
- **Bằng chứng:** Docs: 'the stream will remain open until the delay is complete ... Default: no delay.'; streaming.go `time.AfterFunc(delay, ... h.closeConnections())`. Master reverseproxy.go L211-221: 'retained across config reloads when their upstream still exists in the new config'; grep for 'detach' in v2.11.9 reverseproxy.go, streaming.go, caddyfile.go returned nothing.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/website/master/src/docs/markdown/caddyfile/directives/reverse_proxy.md ; https://raw.githubusercontent.com/caddyserver/caddy/master/modules/caddyhttp/reverseproxy/reverseproxy.go ; https://raw.githubusercontent.com/caddyserver/caddy/v2.11.9/modules/caddyhttp/reverseproxy/streaming.go

### J1-05 · `VERIFIED` — Caddy: access-log timing for upgraded streams

- **Nhận định:** For an upgraded stream Caddy v2.11.9 emits the access-log entry only when the tunnel ends, because the proxy handler blocks until both copy directions finish and request logging is deferred to handler return.
- **Bằng chứng:** reverseproxy.go L1312-1316: `h.handleUpgradeResponse(logger, &wg, rw, req, res)` then `wg.Wait()`; server.go: `defer s.logRequest(accLog, r, wrec, &duration, &writeErr, repl, bodyReader, shouldLogCredentials)`.

### J1-06 · `REQUIRES_VALIDATION` — Caddy: idle timeouts versus long-lived streams

- **Nhận định:** Caddy's server-wide `read_body_idle` and `write_idle` timeouts default to 1m; they should not cut idle upgraded streams because Go clears connection deadlines on hijack, but this must be confirmed with an idle client.

### J1-08 · `VERIFIED` — Routing (a): caveats and the dynamic-a variant

- **Nhận định:** A placeholder upstream counts as one static upstream for health checks and load balancing across all tenants; the alternative `dynamic a` module also expands placeholders in name and port, caches lookups for 1m in a 100-entry cache, and gets no active health checks.
- **Bằng chứng:** Docs: 'potentially many different backends act as a single, static upstream in terms of health checks and load balancing'; 'active health checks do not run for dynamic upstreams'. upstreams.go: `name := repl.ReplaceAll(au.Name, "")`, `if cached.freshness.IsZero() && len(aAaaa) >= 100`, Refresh default `time.Minute`.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/website/master/src/docs/markdown/caddyfile/directives/reverse_proxy.md ; https://raw.githubusercontent.com/caddyserver/caddy/v2.11.9/modules/caddyhttp/reverseproxy/upstreams.go

### J1-09 · `VERIFIED` · *critical* — Routing (a): host-label injection

- **Nhận định:** In a wildcard site the label is attacker-controlled: Caddy's `*` matches any single label unvalidated and `{labels.N}` returns it lowercased; Go only rejects Host bytes outside a lenient set (no slash or braces), so the label must be validated before it forms an upstream name.
- **Bằng chứng:** matchers.go: `if patternParts[i] == "*" { continue }`; replacer.go L330-334 returns `strings.ToLower(hostLabels[len(hostLabels)-idx-1])`; x/net httpguts validHostByte allows letters, digits and `!$%&()*+,-.:;=[]'_~`; net/http server.go L1156 rejects others with 'malformed Host header'.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/caddy/v2.11.9/modules/caddyhttp/matchers.go ; .../caddyhttp/replacer.go ; https://raw.githubusercontent.com/golang/net/master/http/httpguts/httplex.go

### J1-10 · `VERIFIED` · *critical* — Routing (b): per-tenant routes through the admin API

- **Nhận định:** Routing option (b): routes can be appended, inserted or deleted through `POST/PUT/DELETE /config/...` or `/id/<@id>`, but each call regenerates and loads the whole config, i.e. it is a reload with the same stream-closing effect; concurrent writers need `Etag`/`If-Match`.

### J1-16 · `VERIFIED` · *critical* — Certificates: on-demand TLS with ask

- **Nhận định:** On-demand TLS obtains a certificate during the first handshake for an unknown name and must be gated by a global `ask`/permission endpoint (`?domain=<name>`, 2xx allows); Caddy v2.11.9 rejects on-demand policies without one. The first handshake is held during issuance.
- **Bằng chứng:** options.md: 'If the endpoint returns a 2xx status code, Caddy will be authorized to obtain a certificate for that name.' automation.go: 'on-demand TLS cannot be enabled without a permission module to prevent abuse'. automatic-https.md: 'the handshake is held while Caddy obtains a certificate'; 'Restrictions are "global"'.

### J1-21 · `ASSUMED` — Let's Encrypt limits at 10/100/1000 tenants

## Hệ quả thiết kế (agent đề xuất)

- Route tenants with one wildcard site and a label-derived upstream (placeholder or 'dynamic a') so onboarding and offboarding never reload Caddy; reserve reloads for rare global changes, batch them, and set stream_close_delay to avoid an immediate reconnect storm (it only postpones the close).
- Treat the host label as untrusted input: accept only a strict pattern (for example lowercase letters, digits and hyphens of bounded length), build the upstream as fixed-prefix + label + fixed port, and answer everything else locally. Note that CrowdSec LAPI and Headscale both default to port 8080, so an unprefixed pattern could reach the wrong container.
- Do not enable passive or active health checks on a placeholder upstream (state is shared across tenants); use handle_errors for 502/503 and consider 'dynamic a' if per-backend state is needed.
- Keep HTTP/1.1 enabled on the tenant server, proxy to Headscale over plain HTTP/1.1 (no h2c), and never gate routing on a WebSocket-only matcher. HTTP/3 can be disabled for tenant vhosts and UDP 443 left unpublished unless the portal needs it.
- Keep port 80 open and fast-failing: redirect to HTTPS (the client then falls back to 443) and answer /generate_204; a silently dropped port 80 adds a 500 ms delay to every control dial.
- At the edge overwrite True-Client-IP and X-Real-IP with the connecting address and set each instance's trusted_proxies to the edge's address on that tenant network; without both, Headscale logs either the proxy or a spoofable value.
- Apply a path allow-list per tenant vhost so /api/v1, /swagger and /version are never public; let the Go backend reach the Headscale API over the tenant network only, and never publish the metrics (9090) or gRPC (50443) listeners.
- Use a wildcard certificate via DNS-01 for platform subdomains and on-demand TLS with a backend ask endpoint only for customer-owned domains. Scope the DNS token to one zone or CNAME-delegate _acme-challenge, and persist and back up Caddy's /data volume.
- Do not plan on Caddy's internal CA, even for LAN development: Tailscale clients validate /key and DERP against system and Let's Encrypt roots. Use a real domain with DNS-01 and either exempt it from resolver rebinding protection or run split-horizon DNS with public resolvers configured in Caddy.
- Give every tenant its own UDP STUN port with identical container and host numbers, publish it on IPv4 explicitly unless the Docker network is IPv6-enabled, and plan a later move to a shared STUN-only node on 3478 through a custom DERP map.
- Configure Docker default-address-pools before the first tenant (small subnets, away from the LAN's 192.168.0.0/16 and from 100.64.0.0/10), use one bridge and one Compose project per tenant, attach the edge at runtime and pin its default gateway with gw-priority.
- Put host firewall rules for published ports in DOCKER-USER (or an nftables forward-hook table), not in ufw or INPUT; use them for UDP STUN rate limits and, if wanted, the CrowdSec firewall bouncer.
- Run one shared CrowdSec with file acquisition of Caddy's default JSON access log from a shared volume (avoids mounting the Docker socket); shorten the bouncer ticker_interval; keep the log's default key names.
- Decide explicitly on Central API sharing and on pulling the community blocklist for tenant vhosts; maintain allowlists for known tenant egress addresses and consider shorter or softer remediation for control-plane hostnames to limit NAT-wide lockouts.
- Answer requests for suspended or unknown tenants with a status that stock scenarios do not count (for example 503 or connection abort) rather than 404/403/400, so legitimate fleets behind one NAT are not banned.
- Because the edge sees only the /ts2021 upgrade, detection of registration or auth-key abuse has to come from Headscale's own logs (a custom CrowdSec parser would be new development) or from backend-side controls.
- If AppSec is used, restrict it to the portal vhost or set appsec_fail_open deliberately; with the default, a CrowdSec outage blocks new requests on every protected site.
- If routing options (b) or (c) are ever used, expose Caddy's admin API to the backend only through a unix socket on a shared volume with tight permissions; a backend compromise then equals full control of the edge.
- Pin plugin versions in the xcaddy build (caddy-ratelimit has no releases, so pin a commit) and stay on Caddy 2.11.5 or newer; a third-party CVE record (CVE-2026-55458, not confirmed upstream in this session) describes header leakage on proxied 101 responses in earlier versions.

## Câu hỏi mở

- Does a single Caddy container remain stable and performant when attached to 100 or 1000 Docker networks (interfaces, embedded DNS, attach latency)? Needs a load test; no documented limit was found.
- Do per-tenant published UDP STUN ports return correct reflexive addresses for external IPv4 and IPv6 clients on the target Ubuntu host (tailscale netcheck / debug derp), and are non-3478 UDP ports acceptable on customer networks?
- Per-tenant embedded STUN ports versus one shared STUN-only node on 3478 via custom DERP maps: which is the phase-1 choice?
- What stream_close_delay value is tolerable, how do real Tailscale clients and Headscale behave when all streams of an old config are closed at once, and should the design wait for a release containing stream_detached?
- Do Caddy 2.11.x default idle timeouts leave idle ts2021 and DERP streams untouched over hours (test required)?
- Does newly attached Docker DNS resolution work for a placeholder upstream without any Caddy reload, and how quickly after 'docker network connect' (test required)?
- Which CrowdSec scenarios fire for realistic tenant traffic behind one NAT address (replay test), and what allowlist or profile policy keeps false positives acceptable?
- Should the platform share signals with CrowdSec's Central API and pull the community blocklist, given tenant privacy expectations and the reduced blocklist tier for non-contributors?
- Is AppSec worth enabling at all for tenant vhosts (only upgrade request headers are inspectable), or only for the portal?
- Which DNS provider hosts the platform zone, can its API token be scoped to one zone, and is CNAME delegation of _acme-challenge preferred?
- IPv6 strategy for the edge: IPv6-enabled Docker networks (ULA plus NAT or routed prefix) or IPv4-only publishing with no AAAA records?
- Do published ports work for a container attached only to an internal network, or must tenant instances keep a non-internal network for STUN (test required)?
- Rate-limit design: which keys (client IP, tenant, path) and limits for /ts2021, /key and /register, and is the unreleased caddy-ratelimit plugin acceptable or should limits live in nftables and the backend?
- How will the backend obtain the Docker privileges needed for network attach and tenant lifecycle without mounting the raw Docker socket into a network-facing service?
- The issue-tracker findings (Headscale #2164, #2129, #1988; Caddy #6420) and CVE-2026-55458 were read only via summarised pages; confirm wording and status upstream before citing them in the design document.
