## H2 - Headscale v0.29.7 embedded DERP, DERP map, /verify endpoint, STUN, and several Headscale instances with relays on one host

**Tóm tắt của agent:** Headscale v0.29.7 (built against tailscale.com v1.104.4) can give every tenant instance its own relay. The embedded DERP is one config switch; it verifies clients by default, in-process and fail-closed, against that instance's node list only, so a node from another tenant is refused. That makes embedded DERP per tenant the natural first relay plane. All of this was established by reading source; nothing was run. What it costs: 1. TLS and the proxy. Clients always dial DERP with TLS on the advertised port, then send GET /derp with Upgrade: DERP. The generated map entry is the server_url host and port, so behind Caddy the relay is tenant-host:443 and Caddy must pass the Upgrade through. Headscale's handler and Caddy's proxy code both support this, but upstream never tests it, the reverse-proxy page is unverified community documentation, and Tailscale tells derper operators not to use HTTP proxies. Caddy also closes upgraded streams on every config reload unless stream_close_delay is set. 2. STUN. A UDP listener is mandatory per instance and cannot go through Caddy. The advertised STUNPort is the listen port, not a Docker-remapped port. STUN is stateless and unauthenticated and clients follow STUNPort, so either a unique UDP port per tenant or one shared responder on udp/3478 is feasible by code reading; the shared variant is simpler but unproven. A STUN-only node has to sit in the same region as the DERP node. STUN through Docker port publishing (source address, IPv6) is undocumented and untested upstream. 3. Operations. No API manages DERP. Config changes need a restart (SIGHUP reloads only policy), and a restart drops that tenant's relayed sessions. There is no rate limiting, no mesh and no relay traffic metrics. 4. Exposure and defaults. /verify is public, unauthenticated and a node-key membership oracle; block it at the edge unless an external derper needs it. The example config loads Tailscale's public DERP map and makes startup depend on that URL; tenant configs should set derp.urls to an empty list and state every DERP key explicitly. Recommendation: plan phase 1 as embedded DERP per tenant behind Caddy, with STUN either shared on 3478 or on per-tenant ports. Gate that decision on four hands-on tests: - DERP through Caddy - STUN through Docker port publishing - shared STUN across tenants - impact of Headscale restart and Caddy reload Keep standalone derper as the fallback and as the basis for later regional relays. It has its own TLS, metrics and rate limits, but must be built from source, and its verify fail-open default must be turned off. A derper shared across tenants needs a custom verify aggregator and gives no tenant separation inside the relay.

### H2-08 · `VERIFIED` · *critical* — Behind a TLS-terminating proxy

- **Nhận định:** With server_url=https://<host> and a plain-HTTP listen_addr behind a TLS-terminating proxy, the generated DERP node is <host>:443, so clients do TLS with the proxy; on the plain DERP path Headscale passes the proxy's TCP address to the relay as the client address.
- **Bằng chứng:** reverse-proxy.md: 'Headscale logs WRN listening without TLS but ServerURL does not start with http:// during startup. This is expected and indicates that the reverse proxy is in charge of terminating TLS.' derp_server.go:279 passes netConn.RemoteAddr().String() to Accept.

### H2-14 · `VERIFIED` — Caddy Upgrade handling

- **Nhận định:** Caddy v2.10.0 reverse_proxy forwards any Upgrade token to the backend and switches protocols when the backend's 101 response names the same token, so 'Upgrade: DERP' is not limited to WebSocket handling.
- **Bằng chứng:** reverseproxy.go:686-710: if reqUpgradeType != '' { req.Header.Set('Connection', 'Upgrade'); req.Header.Set('Upgrade', reqUpgradeType) }; streaming.go:60-80 proceeds only if asciiEqualFold(reqUpType, resUpType). Tag v2.10.0 was read; the deployed Caddy version is not yet fixed.

### H2-15 · `VERIFIED` · *critical* — Caddy reload

- **Nhận định:** By default Caddy v2.10.0 closes all upgraded (hijacked) streams when its proxy config is unloaded on reload; stream_close_delay keeps them open. Without it, each Caddy config change drops the DERP and control streams passing through that proxy.
- **Bằng chứng:** reverseproxy.go:148-155: 'If nonzero, streaming requests such as WebSockets will not be closed when the proxy config is unloaded ... enabling this prevents streams from closing when Caddy's config is reloaded.' streaming.go cleanupConnections closes immediately when StreamCloseDelay == 0.
- **Nguồn:** https://raw.githubusercontent.com/caddyserver/caddy/v2.10.0/modules/caddyhttp/reverseproxy/reverseproxy.go

## Hệ quả thiết kế (agent đề xuất)

- Tenant config generator must write the whole derp block explicitly: enabled true, region_id (900-999), region_code, region_name, verify_clients true, stun_listen_addr, private_key_path on the tenant volume, ipv4/ipv6 of the host, urls: [] and paths. Omitted keys fall back to zero values (region_id 0, no auto-update), and the example's Tailscale URL would make startup depend on an external fetch.
- server_url must be https://<tenant-host> on 443 so the generated relay entry is <tenant-host>:443; Caddy routes by hostname to each instance's plain-HTTP listen_addr and must pass both Upgrade: tailscale-control-protocol and Upgrade: DERP. Per-tenant TCP ports are avoidable and undesirable (requirements.md says clients assume HTTPS on 443 in certain situations).
- Set stream_close_delay on the Caddy reverse_proxy handlers and minimise reloads: by default every Caddy config change closes upgraded streams, which would interrupt DERP and control connections of all tenants whenever a tenant is added or removed.
- STUN cannot pass through Caddy and must be published as UDP. If each tenant gets its own UDP port, bind the same port inside the container (stun_listen_addr 0.0.0.0:<P>, publish P:P/udp), because the advertised STUNPort is the listen port; otherwise use a hand-written region.
- Shared STUN is the simpler target if the test passes: every tenant keeps the automatic region advertising 3478 on the shared IP, tenant STUN listeners stay unpublished inside their containers, and one responder (stund or derper with --derp=false) is published on udp/3478.
- If a hand-written region with a stunonly node is used, put that node in the same region as the tenant's DERP node (a STUN-only region could be chosen as home), and expect node reordering on each refresh; with a fully static map set auto_update_enabled false and accept a restart for map changes.
- Keep verify_clients true everywhere; it is the only relay-level tenant isolation and it is fail-closed. Block /verify at the edge (path rule plus rate limit) unless an external derper needs it, and then allow only the derper's address.
- No DERP API exists: the central backend must own config.yaml / derp.paths files and container lifecycle. DERP setting changes mean a Headscale restart, and a restart interrupts that tenant's relayed sessions, so schedule and communicate them.
- Plan relay observability outside Headscale: per-container network counters, proxy byte counts per tenant host, synthetic client probes. There is no in-process rate limit, so noisy-neighbour control needs host-level shaping per container or a later move of heavy tenants to derper with --rate-config.
- Captive-portal detection will contact Tailscale-operated hosts unless a region with canport80 and an IPv4 plus a port-80 handler echoing X-Tailscale-Challenge is provided, or the disable-captive-portal-detection node attribute named in the 0.29 changelog is granted; decide which is acceptable for a self-hosted platform.
- Option (a): embedded DERP per tenant behind the shared 443 proxy plus a unique UDP STUN port per tenant. Pros: no extra components, default fail-closed tenant isolation, automatic region works. Cons: N published UDP ports and firewall rules, non-standard ports, all relay bytes through Caddy, no metrics or rate limits, relay tied to Headscale restarts. Needs tests: DERP via Caddy, STUN via Docker publishing.
- Option (b): embedded DERP per tenant plus one shared STUN. Pros: a single standard UDP port, no per-tenant port allocation, STUN independent of tenant restarts. Cons: shared dependency (if it fails every tenant falls back to relay-only with a 3 s netcheck penalty), one STUN IP limits NAT classification, hand-written variant is subject to reshuffle and placement rules. Needs tests: shared STUN across two tenants.
- Option (c): standalone derper per tenant. Pros: upstream relay binary with metrics, rate limits and mesh; relay survives Headscale restarts; isolation via that tenant's /verify with fail-open disabled. Cons: build and maintain derper images, derper terminates TLS itself and must not sit behind an HTTP proxy, so each needs its own TCP port or an L4 SNI passthrough plus certificates and a STUN port; two containers per tenant; admission depends on Headscale availability.
- Option (d): one shared derper with a verify aggregator. Pros: one relay to run and monitor, one TCP and one UDP port, natural base for regional relays later. Cons: the aggregator must be built and is security-critical; no tenant separation inside the relay (forwarding by key only); global rather than per-tenant metrics; needs a second public IP or L4 demultiplexing if Caddy owns 443.
- Suggested sequence: phase 1 = option (b) with the automatic region, falling back to (a) if shared STUN fails its test; keep (c) as the fallback if DERP through Caddy fails; design the verify aggregator only when regional shared relays (d) are actually planned.

## Câu hỏi mở

- Does embedded DERP relay correctly through Caddy on 443 with a plain-HTTP Headscale backend (Upgrade: DERP, 101 response), and what throughput and CPU does the double hop give with several tenants?
- Does Docker port publishing preserve the client source IP and port for STUN on IPv4 and IPv6 (bridge with and without userland proxy, versus host networking)? Compare tailscale netcheck global endpoints with the real public address.
- Does one shared STUN responder on udp/3478 serve clients of several tenants whose automatic regions all advertise port 3478 on the shared IP?
- With a hand-written region of embedded DERP node (stunport -1) plus stunonly node, do clients select the region as home, and does node reordering on refresh cause visible DERP reconnects ('derp-region-redefined' in client logs)?
- How long are relayed sessions interrupted on a Headscale restart, and on a Caddy reload with and without stream_close_delay? What stream_close_delay value is safe?
- Does the derper README caveat about DERP servers sharing an IP address matter when the relays belong to different tailnets and are reached through one proxy IP?
- Is a single STUN IP per tenant map acceptable for NAT classification (MappingVariesByDestIP), or should a second STUN endpoint on another IP be added?
- Should clients be allowed to reach Tailscale-operated hosts for captive-portal detection, or should it be disabled by node attribute or served locally via a canport80 region?
- Does blocking /verify at the edge have any side effect? By code reading the embedded relay does not use the HTTP listener for verification, but this was not run.
- After deleting derp_server_private.key and restarting, do clients reconnect without any reconfiguration, as the code suggests?
- Can Tailscale peer relay grants (cap/relay, Headscale 0.29.0) carry high-throughput relayed traffic inside a tenant so the embedded DERP stays a low-bandwidth fallback? Not examined in this area.
- Which Caddy version will be deployed? Upgrade and stream-close behaviour was read at v2.10.0 only.
- What relay usage data must the portal show per tenant, given that Headscale exposes none?
