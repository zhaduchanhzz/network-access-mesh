# Research Evidence — C1

> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## C1 - XavierAlpha/derper image (commit e721396) and upstream Tailscale derper v1.104.7

**Tóm tắt của agent:** XavierAlpha/derper is a thin packaging wrapper around upstream cmd/derper: a two-stage Dockerfile (floating golang:alpine and alpine:latest), a 53-line entrypoint that only bootstraps a self-signed certificate, and three workflows. It adds no relay functionality, so every architecture-relevant behaviour is upstream's. Recommendation input: do not use the published image as-is and do not fork; build our own image from the upstream release tag. Reasons, all read today: the image runs as root without a healthcheck; its defaults differ from upstream (VERIFY_CLIENTS=true needing the host tailscaled socket, CERT_MODE=manual, HOSTNAME=127.0.0.1); seven current flags, including -rate-config, have no environment mapping; the repository pins unreleased Tailscale main (1.105.0); automatic rebuilds fire only when cmd/derper changes on main, so `latest` was still v1.104.5 (pushed 2026-11-08) while upstream is v1.104.7; actions are tag-pinned, nothing is signed, the Docker Hub namespace is one user account, and the repository states no licence for its own files. Upstream is BSD-3-Clause, ships no official derper image and documents `go install tailscale.com/cmd/derper@latest` as the build path. Facts the design hinges on: - derper has no tenant concept: one global key-to-connection map; any admitted client can address any connected key. - Admission is checked once, at connect. --verify-clients uses one co-located tailscaled (one tailnet, fail-closed). --verify-client-url takes one URL: POST {NodePublic, Source}, expects 200 with {Allow:true}, 5 s timeout, fail-open by default and only for transport errors. - A relay shared by several Headscale instances therefore needs our own aggregator in front of each tenant's /verify (Headscale v0.29.7 exposes it unauthenticated), run fail-closed, plus a mesh-key tool if revoked nodes must be disconnected immediately. - Rate limiting is a TLS accept limiter plus one experimental global per-connection byte rate; per-tenant accounting is only possible by scraping /debug/clients/?format=json and joining node keys in our backend. - Upstream says not to put derper behind an HTTP proxy or load balancer. It expects TCP 443 and 80 and UDP 3478 directly, has no PROXY-protocol support and gates /debug by source address with loopback allowed, so a same-host passthrough proxy is untested and could expose the debug pages. - TLS is served only on port 443 or with -certmode=manual; manual certificates are loaded once and need a restart on renewal. Self-signed IP certificates pinned through CertName sha256-raw expire after one year. On a single host where Caddy owns 80/443, a standalone derper needs its own public IP, or an alternate DERPPort with manual certificates and STUN published directly. That, and the passthrough question, need a hands-on test before the shared-relay phase is designed in detail.

## Hệ quả thiết kế (agent đề xuất)

- Build our own derper image from the upstream release tag (currently v1.104.7) instead of using or forking this one: digest-pinned Go builder, minimal runtime (the binary is static, CGO_ENABLED=0), non-root user, explicit `-c` path on a volume, no entrypoint script (derper already self-generates IP certificates), release pipeline triggered by upstream tags and base-image updates, image signing.
- A shared relay needs an admission aggregator in the central Go backend: one POST endpoint that takes {NodePublic, Source} and returns HTTP 200 with {Allow: bool} in well under 5 s. derper sends no auth headers, so protect it by network placement or a secret in the URL path. Back it by a central node-key index or by fan-out to each tenant's Headscale /verify.
- Run the shared relay with --verify-client-url-fail-open=false and make the aggregator highly available. Call it directly on the internal network: a reverse proxy answering 502 is treated as a rejection even when fail-open is on, and fail-open only covers transport errors.
- Revocation is not enforced on live connections. If a revoked node must lose relay access immediately, build a small mesh-key client that sends FrameClosePeer; otherwise accept that the node stays connected until its TCP session drops. Treat the mesh key as a top-level secret (file mount only) because it bypasses verification and can observe and close every connection.
- Verification is admission-only, not isolation. On a shared relay any admitted node can address any connected key, so plan a global per-connection limit via --rate-config, monitoring of derp_packets_dropped and /debug/clients, and dedicated relay instances for tenants that need isolation or their own quotas.
- Per-tenant relay accounting must be built in our backend: scrape /debug/clients/?all&format=json, join node keys to tenants, and track deltas because counters are per connection and reset on reconnect.
- derper must terminate its own TLS and be reached directly. On the first single host where Caddy owns 80/443, a standalone derper needs a second public IP, or an alternate DERPPort with -certmode=manual and -http-port=-1 (CanPort80 false). UDP 3478 must be published directly and never rate-limited.
- Caddy and CrowdSec cannot inspect or filter DERP sessions (custom binary protocol inside derper's own TLS). Abuse controls for the relay are derper's accept limiter, --rate-config, the verify URL and L3/L4 firewall rules on inbound traffic only.
- Lock down /debug: scrape metrics over loopback or set TS_DEBUG_TRUSTED_CIDRS to the monitoring subnet, and never front derper with a same-host proxy that connects from 127.0.0.1. The debug pages are also reachable on port 80.
- Prefer a real DNS hostname with built-in Let's Encrypt for the shared relay (automatic rotation). If IP-only, prefer -acme-ip-certs over a self-signed certificate with a CertName pin, which expires after one year and would require a coordinated pin update in every tenant's DERP map.
- The backend needs a per-tenant DERP map generator: region IDs from 900-999 (unique only within one tenant's map), one node per region, explicit IPv4/IPv6, STUNPort and DERPPort when non-default, and Tailscale's default regions removed if traffic must stay on our relays.
- Version policy: upgrade derper together with the Tailscale client release the platform supports. If --verify-clients is ever used for a dedicated single-tenant relay, derper and the co-located tailscaled must be the same revision.
- Do not copy the repository's Dockerfile or entrypoint text into our code base without clarifying its licence: the LICENSE file only reproduces Tailscale's BSD-3-Clause notice.

## Câu hỏi mở

- Does derper v1.104.7 work behind a same-host L4 TLS passthrough sharing port 443 with Caddy, what client address does it then see, and is /debug exposed? Needs the lab test named in C1-27 and C1-35.
- Single-host port plan for a standalone relay: second public IP, or alternate DERPPort? Do the client networks we target allow outbound TCP to a non-443 port?
- Aggregator data source: fan-out to N Headscale /verify endpoints (latency grows with tenant count against a 5 s budget) or a central node-key index (how fast must a newly registered node appear before its first DERP connection is rejected)?
- Fail-open or fail-closed for the shared relay, and what availability target does the aggregator then need?
- Is immediate eviction of revoked nodes from the relay a requirement? If yes, validate a derphttp ClosePeer tool with the mesh key against v1.104.7.
- Should Headscale's public POST /verify be blocked at the edge for external callers (node-key membership oracle), and does embedded-DERP verification keep working when it is? Headscale registers an internal transport for the embedded case, which suggests yes, but it needs a test.
- Does `go install tailscale.com/cmd/derper@v1.104.7` build cleanly and reproducibly with a stock Go 1.27.4+ image (Tailscale maintains its own Go toolchain branch)? Test build and compare `derper --version`.
- Is the experimental --rate-config stable enough to rely on, and which per-connection byte rate protects neighbours without hurting legitimate relayed traffic? Needs a load test over forced-DERP paths.
- Does Headscale's DERP map YAML pass CertName, STUNPort, DERPPort and CanPort80 through to clients unchanged (cross-area)?
- For the embedded-DERP-per-tenant phase on one IP, each tenant's STUN listener needs its own UDP port: confirm clients honour a per-tenant STUNPort and that the edge can route /derp upgrades per tenant (cross-area).
- Would Tailscale peer relays, which the docs recommend over custom DERP for throughput, work with Headscale v0.29.7 and reduce the need for a high-capacity shared relay (cross-area)?
- The image config sets HOSTNAME as an image-level variable; whether container runtimes or orchestrators override it in our deployment form was not tested (irrelevant if we build our own image).
