## E2 - Headscale v0.29.7: complete configuration reference and runtime network surface

**Tóm tắt của agent:** Headscale v0.29.7 runs up to four process listeners plus one UDP listener: the main HTTP listener (`listen_addr`; no code default, example 127.0.0.1:8080), the metrics/debug listener (`metrics_listen_addr`; disabled when empty, example 127.0.0.1:9090), a remote gRPC TCP listener (`grpc_listen_addr`, default :50443, started only when Headscale terminates TLS itself or `grpc_allow_insecure` is true), an unauthenticated Unix-socket gRPC server, and a STUN UDP listener when the embedded DERP is enabled. The decisive fact for our design: the REST admin API (/api/v1/*, Bearer API key) and the unauthenticated Swagger UI are served by the same router and port as the client endpoints (/ts2021, /key, /register, /auth, /oidc/callback, /derp). Separation therefore has to be a per-tenant path allow-list in Caddy; the upstream Caddy example proxies every path. The Unix socket is full admin without authentication, /metrics has no access control at all, and /debug/* is only source-IP gated (statsviz even admits any private address). Behind a TLS-terminating proxy (the documented mode: empty tls_* keys, https server_url) remote gRPC is not started, so the central backend should use REST over an internal network. Tailscale clients hard-code /ts2021 at the host root and use a POST upgrade with `Upgrade: tailscale-control-protocol`, so every tenant needs its own hostname and the proxy must pass non-WebSocket upgrades. Cloudflare proxy/tunnel is explicitly unsupported and gRPC "may not be proxied". Runtime reload is narrow: SIGHUP reloads only the policy, `dns.extra_records_path` is file-watched, and the DERP map refreshes on a timer; everything else needs a restart. Policy can be written through the API only with `policy.mode: database`. Configuration is a YAML file (/etc/headscale, ~/.headscale, cwd; `-c` or HEADSCALE_CONFIG) with HEADSCALE_<KEY> environment overrides; the only secret-from-file key is `oidc.client_secret_path`. `configtest` is not side-effect free: it creates keys and opens and migrates the database. Rules worth mirroring in our backend: server_url scheme; server_url host must not equal or sit below `dns.base_domain`; prefixes inside 100.64.0.0/10 and fd7a:115c:a1e0::/48; global nameservers required when `override_local_dns` is true. `trusted_proxies` (new in 0.29, default empty) must be set to Caddy's source CIDR, with Caddy overwriting True-Client-IP and X-Real-IP. SQLite is the supported database (WAL is always on, single connection); PostgreSQL is legacy. The embedded DERP region is derived from server_url and the STUN port from `stun_listen_addr`, so per-tenant STUN needs a port plan or one shared responder. The image is distroless and documented to run read-only with a tmpfs for the socket and volumes for /etc/headscale and /var/lib/headscale. Docker and reverse-proxy setups are community-supported only. Headscale is by design one tailnet per instance, which matches the one-instance-per-tenant plan. Nothing was executed; all findings come from reading source and docs at the pinned tags. Still needing hands-on tests: Caddy/CrowdSec pass-through of the control and DERP upgrades, STUN behind Docker port publishing, API-key bootstrap without exposing the socket, and client behaviour after Noise-key loss.

## Hệ quả thiết kế (agent đề xuất)

- Give every tenant its own hostname on port 443 behind Caddy. Path-prefix multiplexing is impossible because clients use /ts2021 at the host root (E2-51). Run Headscale with empty tls_* keys and an https server_url (E2-33).
- Put a path allow-list in each tenant's Caddy site (E2-59) and answer 404 for everything else, in particular /api/*, /swagger*, /verify and /version (E2-60). The upstream Caddy example proxies all paths, so this is our own addition and needs a test matrix.
- Let the central backend call each tenant's REST API directly on an internal Docker network (http://<tenant>:8080/api/v1) with a per-tenant API key. Remote gRPC stays off automatically when Headscale has no TLS; keep grpc_allow_insecure false (E2-03).
- Treat the Unix socket as root-equivalent for the tenant: keep it on a per-container tmpfs and never share that directory with another container unless it is the trusted bootstrap component (E2-04). Decide how the first API key is minted: docker exec, a one-shot job with the socket volume, or gRPC over the socket.
- Use policy.mode: database so the backend can write policy through PUT /api/v1/policy. File mode would require writing files plus SIGHUP (E2-29).
- Plan restarts as the only way to apply non-policy changes (DNS, DERP, OIDC, prefixes). Use dns.extra_records_path for DNS records that must change at runtime (E2-26, E2-28).
- Bind metrics only on a dedicated monitoring network, or disable it with an empty metrics_listen_addr. /metrics is unauthenticated and statsviz accepts any private source address, so the edge proxy must never be attached to that port (E2-15, E2-18). For /debug from a monitoring subnet use TS_DEBUG_TRUSTED_CIDRS deliberately; otherwise it stays loopback-only (E2-16).
- Set trusted_proxies to the fixed subnet Caddy connects from and make Caddy overwrite True-Client-IP and X-Real-IP (E2-36, E2-37). Feed CrowdSec from Caddy access logs rather than Headscale logs.
- Per tenant: /etc/headscale read-only with a generated config.yaml using absolute paths, a /var/lib/headscale volume (db.sqlite plus WAL files, noise_private.key, derp_server_private.key) and a tmpfs for /var/run/headscale. Back up the key files together with the database (E2-34, E2-40, E2-55).
- Set disable_check_updates: true (otherwise every CLI healthcheck queries GitHub), derp.urls: [] if tenants must not depend on Tailscale's DERP map at start-up, and keep logtail.enabled false (E2-25, E2-49, E2-45).
- DERP/STUN on one host: the embedded region uses the tenant hostname on 443 through Caddy and the STUN port from stun_listen_addr. Either allocate a unique UDP port per tenant with identical container and host port numbers, or keep all tenants on 3478 and publish one shared STUN responder on the host (STUN is stateless and tenant-agnostic). The second option needs a netcheck test (E2-06, E2-48).
- Mirror Headscale's validation in the backend before writing a tenant config: URL scheme, server_url host not equal to or below base_domain, prefixes inside the CGNAT/ULA ranges, global nameservers present when override_local_dns is true, ephemeral timeout above 65s (E2-31, E2-32, E2-38, E2-44).
- Run configtest only in a throwaway container against a scratch data directory, never against a live tenant volume (E2-24).
- Keep HEAD /machine/ping-response reachable, or HA subnet-router probing will mark routers unhealthy (E2-14).
- Never set HEADSCALE_DEBUG_TAILSQL_ENABLED, HEADSCALE_DEBUG_DUMP_CONFIG, TS_ALLOW_DEBUG_IP or TS_DEBUG_KEY_PATH in tenant containers outside a lab (E2-07, E2-16, E2-19).
- SQLite per tenant matches upstream's supported path; keep PostgreSQL for our own backend only (E2-41). Because WAL is always on, take backups with a SQLite-aware method or with the container stopped (E2-40).
- Record as a project risk that Docker and reverse-proxy deployments are community-supported only, so regressions there are ours to detect (E2-54).

## Câu hỏi mở

- Does Caddy with the CrowdSec bouncer (and any AppSec/WAF layer) pass POST /ts2021 with Upgrade: tailscale-control-protocol and the DERP upgrade, and do long-lived streams survive Caddy config reloads when tenants are added? Test: tailscale up, tailscale netcheck and tailscale debug derp <region> through the edge, then reload Caddy.
- API-key bootstrap and rotation: which component may touch the tenant socket or run docker exec, and how are keys rotated before the documented 90-day default expiry (docs/ref/api.md lines 7-8)?
- STUN on one host: unique UDP port per tenant versus one shared responder on 3478. Does Docker port publishing preserve the client source address for IPv4 and IPv6 so STUN answers are correct? Test with tailscale netcheck from an external network.
- Behaviour after Noise-key loss or a restore from an older backup: do registered clients reconnect without re-authentication (E2-35)?
- Effective socket mode when unix_socket_permission is omitted (E2-05), and the effective container user: the release config sets none and the distroless base tag used is not the nonroot variant. Test: inspect the image config and stat the socket, then decide on an explicit non-root user and volume ownership.
- Can list and map settings (trusted_proxies, dns.nameservers.split, oidc.extra_params) be set through environment variables alone, or must every tenant get a generated YAML file? config.go lines 915-917 note that UnmarshalKey is not environment-compatible.
- Docker network layout: one shared edge network (tenants can reach each other's port 8080 and metrics port) versus one network per tenant (address-pool limits). Which isolation level do we require?
- Shared or regional DERP later: derper accepts a single --verify-client-url and fails open by default (tailscale v1.104.7 cmd/derper/derper.go lines 83-85). Do we build a verification aggregator across tenants' /verify endpoints, or keep embedded DERP per tenant?
- Does HEADSCALE_DEBUG_DUMP_CONFIG print secrets? The dump uses spew, to which the json:"-" redaction used by /debug/config presumably does not apply. Relevant only if someone enables it for support.
- Does fsnotify pick up an atomic replace of a single bind-mounted extra-records file, or must the parent directory be mounted?
- Per-instance memory and idle CPU for N tenants on one host, and the reconnect load during fleet upgrades. Upgrades must go one minor version at a time and downgrades are blocked (CHANGELOG.md lines 361-364).
- Is /health needed publicly for external uptime checks, or are internal checks enough? From the host, a published 127.0.0.1:9090 port will not count as loopback inside the container, so /debug access from the host also needs a decision.
