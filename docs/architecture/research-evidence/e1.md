# Research Evidence — E1

> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## E1 - Headscale v0.29.7: scope, compatibility, requirements, database guidance, upgrade rules, scaling/HA statements, releases

**Tóm tắt của agent:** Headscale v0.29.7 (2026-10-30) is the latest stable release, a security release, and the version served at headscale.net/stable. It is usable as the per-tenant control plane, but only in the shape upstream designs for: one process, one tailnet, one SQLite file. The design goal is explicit ("a narrow scope, a single Tailscale network (tailnet), suitable for a personal use, or a small open-source organisation") and nothing in the docs offers multi-tenancy, so one tenant = one Headscale instance is the only available mapping. Decisions the evidence supports: - Database: use per-tenant SQLite. Upstream recommends it and calls PostgreSQL "maintenance mode" and "highly discouraged". SQLite runs in WAL mode through a one-connection pool, so treat each instance as a singleton. - Clients: every 0.29.x release requires Tailscale v1.80.0 or newer (capability version 113), enforced with HTTP 400. The 0.29.7 changelog recommends v1.104.4 or newer, but v1.104.x is beyond the capability table and named test matrix shipped in the tag, so v1.104.7 needs our own compatibility test. - Upgrades: one minor at a time on the latest patch, enforced at startup since 0.29.0; minor downgrades are refused. Fleet upgrades need an orchestrator with a cold backup of the config and data directories, and restore as the only rollback. - HA and scaling: nothing exists for the control server. State is partly in memory and the FAQ says it "can likely handle 100s of devices" with little change. Plan for restart, restore, tenant size limits and host sharding, not clustering. Main risks: - Our deployment model is outside upstream support: the README says "we do not support nor encourage the use of reverse proxies and container". Caddy must pass a POST-based upgrade with `Upgrade: tailscale-control-protocol`, Cloudflare proxying is unsupported, and STUN (udp/3478) must be exposed directly, which on a shared IP means one UDP port per tenant (untested). - The image is distroless with no shell, runs as root by default, has entrypoint /ko-app/headscale and declares no health check; the documented check is `headscale health`. - API churn: every minor from 0.26 to 0.29 changed API, CLI, config or policy semantics. Unreleased 0.30 removes gRPC, replaces the v1 REST API and its error format, and adds an OAuth-based v2 API. The backend needs a versioned adapter and should use REST, not gRPC. - Policy can be written through the API only with `policy.mode: database`. DNS, DERP and OIDC are config-file settings that need a restart. - There is no SECURITY.md, no published support policy and no GitHub advisories. Fixes appear only on the newest minor line, so staying current is the only way to receive security fixes. The licence is BSD 3-Clause, which does not obstruct commercial use.

## Nhận định

### E1-01 · `VERIFIED` · *critical* — Scope: single tailnet

- **Nhận định:** Headscale's stated design goal is a narrow scope: one server implements a single tailnet, aimed at self-hosters and hobbyists and 'suitable for a personal use, or a small open-source organisation'. The same paragraph appears in the README, docs index, FAQ and DEB package description.
- **Bằng chứng:** README.md 'Design goal': 'It implements a narrow scope, a _single_ Tailscale network (tailnet), suitable for a personal use, or a small open-source organisation.' Identical text in docs/index.md, docs/about/faq.md and .goreleaser.yml (nfpms description).
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/README.md

### E1-02 · `UNSUPPORTED` · *critical* — Scope: multi-tenancy

- **Nhận định:** Headscale has no multi-tenancy: none of the 30 pages in the v0.29.7 documentation offers a feature, setting or statement for multiple tailnets, organisations or tenant isolation inside one instance. One tenant therefore needs one Headscale instance.
- **Bằng chứng:** Design goal says 'a _single_ Tailscale network (tailnet)'. Every page in the mkdocs.yml nav was read or keyword-scanned (tenant, tailnets, multi-tenan): only an unrelated Entra ID '<tenant-UUID>' in oidc.md matched; the features.md checklist has no such entry.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/about/features.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/mkdocs.yml

### E1-03 · `VERIFIED` · *critical* — Scope: audience

- **Nhận định:** Maintainers state Headscale 'is not enterprise software' and focuses on 'homelabbers and self-hosters'; commercial use is not prevented, but performance 'is not part of the consideration' during development. The project is reverse-engineered and 'not associated with Tailscale Inc.'

### E1-09 · `VERIFIED` — Client compatibility: enforcement

- **Nhận định:** The minimum version is enforced server-side: a client whose capability version is below the floor is rejected with HTTP 400 'unsupported client version' at the Noise handshake, on map and register requests and, since 0.29.3, on /key. The check is a lower bound only.
- **Bằng chứng:** noise.go: `return version >= capver.MinSupportedCapabilityVersion` and `http.Error(writer, unsupportedClientError(version).Error(), http.StatusBadRequest)`. CHANGELOG 0.29.3: 'Reject `/key` requests below the supported capability version floor, matching `/ts2021`'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/noise.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/handlers.go

- **Nhận định:** Stated requirements are a server with a public IP (dual-stack recommended), Headscale served via HTTPS on port 443, a reasonably modern Linux or BSD and a dedicated local user. HTTP or another port is possible, but HTTPS on 443 is 'strongly recommended for production setups'.
- **Bằng chứng:** requirements.md: 'A server with a public IP address for headscale. A dual-stack setup with a public IPv4 and a public IPv6 address is recommended.' Footnote: 'The Tailscale client assumes HTTPS on port 443 in certain situations.'

### E1-15 · `VERIFIED` · *critical* — Requirements: reverse proxy behaviour

- **Nhận định:** A reverse proxy must pass the Tailscale control protocol: a WebSocket-style upgrade performed with POST and the header value `Upgrade: tailscale-control-protocol`. STUN udp/3478 must be served directly and gRPC 'may not be proxied'. A community Caddyfile example (reverse_proxy to 127.0.0.1:8080) is provided.
- **Bằng chứng:** reverse-proxy.md: 'The POST method is used to upgrade the WebSocket connection.' 'The value for the `Upgrade` header is `tailscale-control-protocol`.' Limitations: '[gRPC] (used to remote control Headscale) may not be proxied.'
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/integration/reverse-proxy.md

### E1-17 · `VERIFIED` — Requirements: TLS

- **Nhận định:** TLS can come from built-in ACME (HTTP-01 needs port 80, TLS-ALPN-01 needs port 443), from an operator-supplied certificate (full chain required), or from a reverse proxy with tls_cert_path and tls_key_path empty and an https server_url, in which case a startup warning is expected.
- **Bằng chứng:** tls.md: 'Headscale only supports two values for `tls_letsencrypt_challenge_type`: `HTTP-01` (default) and `TLS-ALPN-01`.' 'The certificate should contain the full chain'. reverse-proxy.md: 'Headscale logs `WRN listening without TLS but ServerURL does not start with http://` ... This is expected'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/tls.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/integration/reverse-proxy.md

### E1-18 · `VERIFIED` · *critical* — Requirements: embedded DERP and STUN

- **Nhận định:** Embedded DERP is off by default; enabling it requires an https server_url and stun_listen_addr (default 0.0.0.0:3478). The advertised region (default ID 999) takes host and port from server_url and its STUN port from stun_listen_addr. With `derp.urls: []` it is the only relay: 'a single point of failure'.
- **Bằng chứng:** config-example: 'The Headscale server_url defined above MUST be using https, DERP requires TLS to be in place'; 'stun_listen_addr MUST be defined'. derp_server.go GenerateRegion: `localDERPregion.Nodes[0].STUNPort = portSTUN`. derp.md warning 'Single point of failure'; Limitations: 'no speed or throughput optimisations'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/ref/derp.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/derp/server/derp_server.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/config-example.yaml

### E1-19 · `VERIFIED` · *critical* — Requirements: trusted proxies and real client IP (0.29.0)

- **Nhận định:** Since 0.29.0 the `trusted_proxies` option gates client-IP headers: True-Client-IP, X-Real-IP and X-Forwarded-For are ignored unless the TCP peer is inside a listed CIDR. The default is empty, and 0.0.0.0/0 and ::/0 are rejected. Previously the headers were honoured from any client.
- **Bằng chứng:** CHANGELOG 0.29.0: 'Add `trusted_proxies` to gate `True-Client-IP` / `X-Real-IP` / `X-Forwarded-For` (previously honoured from any client)'. config.go: `errors.New("0.0.0.0/0 and ::/0 are not allowed")`. config-example: `trusted_proxies: []`.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/CHANGELOG.md ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/types/config.go

### E1-24 · `VERIFIED` — Database: SQLite pragmas and WAL

- **Nhận định:** SQLite is opened with busy_timeout=10000 ms, journal_mode=WAL, auto_vacuum=INCREMENTAL, wal_autocheckpoint=1000, synchronous=NORMAL, foreign_keys=ON and _txlock=immediate. Config keys are database.sqlite.write_ahead_log (true) and wal_autocheckpoint (1000). The defaults already select WAL and openDB has no branch that sets another journal mode.
- **Bằng chứng:** sqliteconfig/config.go Default(): `JournalMode: JournalModeWAL, AutoVacuum: AutoVacuumIncremental, WALAutocheckpoint: 1000, Synchronous: SynchronousNormal, ForeignKeys: true, TxLock: TxLockImmediate`; `DefaultBusyTimeout = 10000`. db.go: `if cfg.Sqlite.WriteAheadLog { sqliteConfig.JournalMode = sqliteconfig.JournalModeWAL`.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/sqliteconfig/config.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/db.go

### E1-25 · `VERIFIED` — Database: single connection

- **Nhận định:** Headscale opens SQLite through a pure-Go driver (CGO disabled) with the connection pool limited to exactly one connection, so one process holds a single database connection. On shutdown with WAL enabled it runs VACUUM.
- **Bằng chứng:** db.go: 'The pure Go SQLite library does not handle locking in the same way as the C based one and we can't use the gorm connection pool', then `sqlDB.SetMaxIdleConns(1)`, `sqlDB.SetMaxOpenConns(1)`. Close(): `db.Exec("VACUUM")`. .goreleaser.yml: `CGO_ENABLED=0`.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/db.go

### E1-26 · `VERIFIED` — Database: PostgreSQL handling

- **Nhận định:** PostgreSQL is a second-class path: pool defaults are max_open_conns 10, max_idle_conns 10 and conn_max_idle_time_secs 3600; startup schema validation runs on SQLite only; the 0.27.0 integrity migration improved SQLite only; there is no official PostgreSQL-to-SQLite migration tool (a community tool is listed).
- **Bằng chứng:** db.go: 'This is currently only done on sqlite as squibble does not support Postgres and we use our sqlite schema as our source of truth.' CHANGELOG 0.27.0: 'PostgreSQL databases are not affected.' FAQ: 'does not provide a tool to migrate from PostgreSQL to SQLite'.
- **Nguồn:** https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/hscontrol/db/db.go ; https://raw.githubusercontent.com/juanfont/headscale/v0.29.7/docs/about/faq.md

### E1-27 · `ASSUMED` · *critical* — Database: several processes on one database

- **Nhận định:** No document read addresses running several Headscale processes against one database. Node state (NodeStore), route state and pending registrations live in process memory and SQLite uses a one-connection pool, so each instance should be treated as a single-process, single-writer service.

## Hệ quả thiết kế (agent đề xuất)

- The tenancy boundary must be one Headscale process per tenant with its own data directory (SQLite file, Noise and DERP private keys) and its own config file; there is no in-instance tenant isolation to reuse.
- Keep each tenant on SQLite inside its own volume and reserve the central PostgreSQL for platform metadata only. Do not point tenant instances at PostgreSQL (upstream: maintenance mode, highly discouraged).
- Run exactly one replica per tenant and never start two processes on the same data directory. Availability comes from restart, monitoring and restore, not from clustering.
- Caddy must terminate TLS on 443 per tenant hostname and proxy to that tenant's listen_addr. Set trusted_proxies to Caddy's source CIDR and have Caddy overwrite True-Client-IP and X-Real-IP. Verify that Caddy and CrowdSec pass the POST upgrade with 'Upgrade: tailscale-control-protocol' and long-lived streams.
- Do not publish /api/v1, /swagger, the gRPC port (50443) or the metrics and debug port (9090) at the public edge; reach them only from the backend network. gRPC cannot be proxied and is removed in 0.30, so the Go backend should use the REST API.
- Never put a Cloudflare proxy or tunnel in front of tenant control endpoints; use DNS-only records.
- Embedded DERP per tenant needs a directly exposed UDP STUN port per instance. On one public IP each tenant needs a distinct STUN port, and because the advertised port is read from stun_listen_addr, the container port and the published host port must be the same number. Validate with real clients before committing to this layout.
- Set derp.urls deliberately: the default pulls Tailscale's public DERP map, while an empty list makes the tenant's embedded DERP the only relay and a single point of failure.
- Tenant settings that are not in the API (DNS, DERP, OIDC, prefixes, TLS, trusted_proxies) must be rendered into config.yaml by the backend and applied by restarting the instance; validate with 'headscale configtest' first. SIGHUP reloads policy only.
- Use policy.mode: database for portal-managed policy (PUT /api/v1/policy, POST /api/v1/policy/check). Write policy templates with grants and 'user@' references, do not rely on '*' meaning all IPs, and avoid autogroup:self by default for larger tenants.
- Put the Headscale API behind a versioned adapter in the Go backend: 0.26 to 0.29 each changed API or CLI semantics, and 0.30 replaces the v1 REST API, its error format and credential IDs and adds an OAuth-based v2 API. If the CLI is ever used remotely it must match the server version.
- Model nodes as either user-owned or tagged (never both, no moves between users). Pre-auth keys and API keys are shown once, so the backend must capture and encrypt them at creation and track them by ID. API keys expire (default 90 days), so schedule rotation.
- Build a fleet upgrade orchestrator: per tenant stop, cold-copy config and data directories, move the image tag by one minor (latest patch), start, health-check. Rollback is a restore of the backup because minor downgrades are refused. Keep a canary tenant and record each tenant's version.
- Enforce a client floor in onboarding and the portal: v1.80.0 today, v1.84.0 once 0.30 is adopted, and recommend v1.104.4 or newer for the SSH fixes. Check node client versions before each minor upgrade.
- Container hardening is our responsibility: the image runs as root and has no shell. Override the user, pre-create volume ownership, use a read-only root with tmpfs /var/run/headscale, use 'headscale health' as the health check (there is no curl in the image) and pin images by digest. Keep the -debug tag for troubleshooting.
- Plan capacity per tenant in the low hundreds of devices until load-tested, scrape Prometheus metrics internally, and shard tenants across hosts by size and churn.
- Because upstream does not support containers or reverse proxies, own an integration test suite (official clients through Caddy on every supported OS) and reproduce problems without the proxy before reporting upstream.
- Run NTP on the hosts and do not join the Docker host to a tenant tailnet: time sync is undocumented upstream but TLS, OIDC and key expiry depend on it (assumption), and a same-host Tailscale client is explicitly unsupported.
- Subscribe to the releases feed and treat every new patch release as a security update: there are no GitHub advisories and no published support policy to rely on.

## Câu hỏi mở

- Does Tailscale v1.104.7 interoperate fully with Headscale v0.29.7 on Linux, Windows, macOS, iOS and Android (registration, DERP, MagicDNS, SSH, routes)? Needs a hands-on matrix test.
- Does Caddy with CrowdSec correctly proxy the control-protocol upgrade and the embedded DERP endpoint (/derp), including long-lived connections?
- Can several tenant instances with embedded DERP share one public IP using distinct STUN UDP ports, and do all client platforms honour a STUN port other than 3478?
- Which online backup method is right for a WAL-mode SQLite database (stop-and-copy, SQLite backup API, Litestream), and what RPO and RTO does it give? Upstream documents only cold copies.
- What happens to registered clients if a tenant's noise_private.key or DERP key is lost or regenerated during a restore?
- Does the image run correctly as a non-root user with a read-only root filesystem and a tmpfs socket directory?
- What are the idle and loaded CPU and memory costs per tenant instance, the maximum tenants per host, and the practical device ceiling per tenant under churn?
- How do connected clients behave while a tenant's control plane is down or restarting (existing tunnels, reconnect storm on restart)?
- When will 0.30.0 ship, and should the backend target the v1 REST API, the new OAuth-based v2 API, or both behind an adapter?
- Which Headscale versions receive security fixes? No policy is published; confirm with the maintainers or assume latest minor only.
- How will the portal obtain each node's client version and OS? The v1 Node message has no such field.
- Is a restart acceptable for tenant DNS, DERP and OIDC changes, and how long does a restart take given the VACUUM on shutdown?
- Decision needed: per-tenant policy in database mode (API-managed) or file mode (rendered by the backend plus SIGHUP).
