> Một phần của [nhật ký bằng chứng nghiên cứu](../research-evidence.md) (P0-T08). Chép nguyên từ kết quả của research agent ngày 2026-11-16; nhận định và trích dẫn giữ nguyên tiếng Anh.

## B1 - fzhzyh/headscale-admin: backend core and security (commit 0a4ca5e92c992bc4dff17d84f8c8c12856f1db69)

**Tóm tắt của agent:** Verdict for B1: do not adopt this backend; use it as a reference. The server is a 46-file, 11,627-line Node 22 / Fastify 5 / TypeScript monolith on a synchronous node:sqlite database. Comments, logs, API messages and role names are all Simplified Chinese, and the newest 20 commits carry one author identity over about two and a half weeks. Everything assumes exactly one Headscale: one module-level REST client, global settings keys for URL and API key, module-level cache cells, poll snapshots and WebSocket hub, and no tenant or instance column in any of its 20 tables. RBAC is 27 global permission strings with four built-in roles and no resource scoping; holders of paneluser:write or group:write can make themselves superuser. Making it tenant-aware on PostgreSQL would touch every table, about 100 handlers and 40+ direct client call sites, and would still leave us on a stack we did not choose. That is rewrite-level effort with inherited risk. Sound parts worth porting to Go: - Headscale stays authoritative and is reached only through REST; the panel never opens Headscale's SQLite file and cannot edit its config, restart it or touch Docker. - The thin client covers 27 of the 29 operations in the v0.29.7 OpenAPI file and documents real v0.29 REST quirks. - A 2-second single-flight read cache invalidated by a write epoch, and a poll-diff-fan-out WebSocket hub. - Revocable server-side sessions with a CSRF header token, masked AES-GCM secret settings, self-lockout guardrails, a clean audit event taxonomy, and constrained-intent AI drafting that never auto-applies. Security quality is uneven. Substantiated weaknesses: - Username-only lockout that allows denial of service. - 32-bit recovery codes stored as unsalted SHA-256; unhashed session IDs and OAuth tokens. - Unconditional trustProxy. - A mandatory PANEL_SESSION_SECRET that no code reads. - Best-effort audit writes with no tamper evidence. - A settings role that can repoint hs.url and receive the Headscale API key. - No Headscale version detection, gRPC, key rotation or retries. The built-in OIDC provider (the panel as issuer trusted by Headscale) should not be reused. Its token endpoint has no form-urlencoded parser, while Headscale's Go client posts form-encoded bodies and the project's own test posts JSON, so real logins probably fail. In addition, access_token equals a 30-day refresh token, nothing is revocable, deactivated users keep working tokens, and email_verified is never emitted although Headscale v0.29.7 requires it by default for email filters. Use an established IdP per tenant instead. Three items are inferred from code and need a hands-on test before being cited as fact: the OIDC token-exchange failure, a percent-encoded path that probably skips the global auth gate, and a probably ineffective guard against deleting the panel's own API key.

### B1-09 · `VERIFIED` — Lockout and rate limiting

- **Nhận định:** Brute-force defence: per-IP limits (login 20 per 300 s, 2FA 30 per 5 min) plus a username-keyed lockout (5 failures in 900 s) that ignores IP and counts attempts made while locked, so any known username can be kept locked out. The 2FA step skips the lockout check and its challenge IDs use Math.random.

## Hệ quả thiết kế (agent đề xuất)

- Do not adopt this backend. Build the Go/PostgreSQL control plane and use this repository as a reference for Headscale 0.29 REST behaviour and for a handful of patterns.
- Keep Headscale authoritative and reach it only through its API, never its SQLite file. Note that Headscale v0.29.7 defaults policy.mode to 'file' (hscontrol/types/config.go L444), so each tenant instance must be configured for database mode before API policy writes work.
- Model tenancy from the first migration: tenant registry, per-tenant Headscale endpoint and credential, tenant key on every table, and a per-tenant client factory instead of a global client.
- Never let a tenant-level role edit the Headscale base URL. Derive it from the tenant registry and allow-list internal addresses, because whoever controls the URL receives the API key.
- Store per-tenant API keys with envelope encryption and keep the key-encryption key outside the database volume; plan rotation and expiry monitoring, which this project lacks.
- Split RBAC into platform roles and tenant roles with scoped bindings (user, role, tenant), add grant containment, and keep 'manage administrators' separate from every other permission.
- Use revocable server-side sessions with hashed identifiers, a CSRF header token, enforceable MFA for platform admins, and throttling keyed on account plus source so that lockout cannot be used for denial of service.
- Authorise on the router's decoded path with deny-by-default per-route middleware; do not gate on raw URL prefixes.
- Configure an explicit trusted-proxy list in the backend and make the edge proxy overwrite X-Forwarded-For; add security headers at the edge because nothing here sets them.
- Do not reuse the built-in OIDC provider. If tailnet logins need an IdP, use an established one per tenant and ensure it emits email_verified. Headscale v0.29.7 defaults only_start_if_oidc_is_available to true (config.go L483), so each tenant's Headscale start depends on IdP availability.
- Port the realtime design as per-tenant poll-diff-fan-out with tenant-scoped channels, Origin checks and session re-validation; budget polling cost as tenants times ListNodes per interval, since Headscale has no streaming API.
- Add Headscale version and capability detection to the Go client, centralise version quirks in one package, and add retries with backoff.
- Make audit tenant-aware and tamper-evident (append-only or chained, shipped to an external sink), and do not swallow audit failures for high-risk operations.
- This panel has no lifecycle control (no config editing, restart or Docker access). Our platform needs its own narrowly scoped provisioning component rather than mounting the Docker socket into the API service.
- DNS extra records are a file integration, not an API: the orchestrator must own one extra-records file per tenant on a volume shared with that tenant's Headscale.
- If AI policy drafting is ported, keep the constrained-intent approach, make it tenant opt-in with an outbound allow-list, and treat prompts as data leaving the system.

## Câu hỏi mở

- Hands-on: does a Headscale v0.29.7 OIDC login against this provider fail at token exchange with HTTP 415, as the code suggests?
- Hands-on: does an unauthenticated GET /%61pi/realtime/status succeed, and can a must-change-password session reach other routes through an encoded path?
- Hands-on: on v0.29.7 with a new-format key, can the UI delete the panel's own API key despite the guard?
- Are the REST quirks documented for v0.29.6 (query-string binding for ExpireNode, RegisterNode, DeletePreAuthKey; 400 'acl policy not found') still true on v0.29.7, and how stable are they across the next minor release?
- Decision: REST or gRPC for our Go client, and how each tenant instance is reached and authenticated (API key over TLS on an internal network versus another channel).
- Decision: which identity provider serves tenant users, and whether portal administrators should also be tailnet identities.
- Load test: how many tenants and nodes can a 15-second poll-and-diff design sustain before ListNodes cost becomes a problem?
- Decision: where per-tenant API keys and the key-encryption key live, and the rotation cadence given Headscale API keys expire.
- Edge configuration: confirm our Caddy setup overwrites client-supplied X-Forwarded-For so audit and throttling see real client addresses.
